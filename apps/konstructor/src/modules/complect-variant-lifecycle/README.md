# Жизненный цикл варианта комплекта

Сервис `ComplectVariantLifecycleService` двигает элементы смарта
`complect_variant` по стадиям. Сейчас реализован **только финал** — «Успех» и
«Не состоялся». Остальные стадии уже заведены в смарте, но их никто не ставит.
Этот файл — задача на будущую работу: что должно ставиться, кем и чего для
этого не хватает.

## Что сделано сейчас

| Когда | Кто | Что ставит |
| --- | --- | --- |
| вариант уехал в сервисную сделку (робот поставки/перезаключения) | `InitDealUseCase.closeSourceVariants` → `markSuccess` | `cvar_success` («Успех») исходному элементу |
| вариант остался на сделке и не был закрыт раньше | тот же шаг → `markRejected` | `cvar_failed` («Не состоялся») |
| менеджер нажал «Сделать текущим» / «Отклонить» | легаси-фронт, `complect-variant-thunk` | `cvar_current` / `cvar_rejected` |

Важно: `cvar_rejected` («Отклонён») ставит **только человек**, робот его не
пишет. Автоматический «не доехал» — это отдельная стадия `cvar_failed`. Иначе в
разборе слиплись бы две разные причины: «клиент отказался от набора» и «набор
просто не выбрали».

Шаг в роботе — best-effort: он обёрнут в `try/catch`, и его падение не роняет
создание сервисной сделки. Сервис внутри тоже ничего не требует: нет смарта,
нет прав, у типа выключены стадии — тихо ничего не делает и пишет warn.

## Почему только успех/отказ

Заказчик просил и стадии продажи (КП → счёт → договор → поставка →
согласование), но за каждой из них стоит свой поток обслуживания сущности:
событие, которое её включает, поле, где хранится результат, и правило, что
делать при переделке. Этих событий в коде **нет** — см. «чего не хватает».
Делать стадию, которую никто не ставит, вредно: в канбане появляется колонка,
которая всегда пуста, и пользователь считает, что система сломана.

Поэтому стадии **заведены в дескрипторе сразу** (чтобы не переустанавливать
смарт второй раз: повторная установка доливает стадии безопасно, а вот
переименование кода ломает элементы), а простановка — по мере появления
событий.

## Планируемый flow

### 1. `cvar_offer` — «КП»

**Когда:** сгенерировано коммерческое предложение, в которое вошёл вариант.

**Кто триггерит:** генерация КП. Для нового фронта — `offer-word/multi`, для
легаси — N обычных запросов из `complect-variant/lib/build-offer-requests.ts`.
Правильная точка одна: ручка генерации на бэке, потому что только она знает
итоговый состав участников.

**Чего не хватает:** в запрос генерации не приходит список `variantSmartId`
участников как отдельное поле — он выводится из `variants[]` DTO. Нужно либо
гарантировать наличие `variantSmartId` у каждого элемента `variants[]`, либо
передавать плоский список id. Плюс решение: ставить ли стадию, если КП
перегенерировали (сейчас это обычная операция — переделывают по многу раз).
Предложение: ставить стадию только «вперёд», т.е. не откатывать вариант с
`cvar_contract` обратно на `cvar_offer` — для этого сервису нужен метод
`markStageForward`, сравнивающий `sort` текущей и целевой стадии.

### 2. `cvar_invoice` — «Счёт»

**Когда:** по варианту выставлен счёт.

**Кто триггерит:** ручка генерации счёта (`invoice-template`).

**Чего не хватает:** счёт сейчас привязан к **сделке**, а не к варианту. В
DTO счёта нет `variantSmartId`, и связи «этот счёт — про этот набор» не
существует. Нужно поле-ссылка в шаблоне счёта либо соглашение «один счёт на
вариант». Пока этого нет, стадию ставить не с чего.

### 3. `cvar_contract` — «Договор»

**Когда:** по варианту сформирован (подписан) договор.

**Кто триггерит:** контрактный тхунк фронта → `document-contract` на бэке; для
мультикомплектности — `konstructor/init-supply`, который уже принимает
`variants[]` и делает страницу таймлайна на участника.

**Чего не хватает:** различить «договор сформирован» и «договор подписан» в
коде нечем — события подписания нет. Реалистичный вариант: ставить стадию в
момент `init-supply`, когда вариант попал в заявку RPA со своим договором, и
считать это «договор ушёл в работу».

### 4. `cvar_supply` — «Поставка»

**Когда:** по варианту создан отчёт/процесс о поставке.

**Кто триггерит:** `document-supply-report` (создание отчёта) — чужая зона,
интеграция делается отдельной задачей.

**Чего не хватает:** отчёт о поставке тоже не знает про вариант. Нужна та же
связь `variantSmartId` в DTO отчёта, что и в счёте.

### 5. `cvar_approval` — «Согласование»

**Смысл:** это **интервал**, а не событие: время между «создали отчёт/процесс о
поставке» и «поставка завершена». Ради него стадия и нужна — чтобы в канбане
было видно, сколько наборов висит в приёмке и по сколько дней.

**Кто триггерит:** вход — тот же, что у `cvar_supply` (можно объединить:
`cvar_supply` = отчёт создан, `cvar_approval` = процесс согласования пошёл);
выход — приёмка.

**Чего не хватает:** отдельного события «поставка принята» в коде **нет**.
Единственная существующая точка — срабатывание робота RPA на стадии приёмки
заявки, который дёргает `POST supply/init-deal`. Варианты решения:
1. считать приёмкой сам вызов `supply/init-deal` (так сделано сейчас: `markSuccess`);
2. завести второго робота на стадии приёмки и новую ручку (например
   `supply/accept`), которая проставит вариантам `cvar_success` — тогда
   `init-deal` будет ставить `cvar_approval`, а приёмка `cvar_success`.

Вариант 2 честнее, но требует настройки робота на портале — это решение
заказчика, не разработки.

### 6. Переделка

«Если переделывают, надо их тоже актуализировать». Сценарий: набор уже уехал
(`cvar_success`), но клиент передумал, и его собирают заново. Что должно
происходить:

- новый вариант создаётся **новым элементом** (`cvar_draft`), а не правкой
  закрытого — иначе теряется история периода;
- закрытый элемент остаётся в `cvar_success`: это факт прошлого;
- если переделка отменяет поставку целиком — нужен ручной откат стадии, и для
  него понадобится метод `markStage` из UI (кнопка «вернуть в работу»).

**Чего не хватает:** правила, что считать «переделкой»: правка существующего
варианта, создание нового или отмена заявки RPA. Вопрос к заказчику.

## Чего не хватает — сводно

| Не хватает | Где | Блокирует |
| --- | --- | --- |
| события «поставка принята» | портал (робот RPA), ручки `supply/accept` нет | `cvar_approval` → `cvar_success` по факту |
| связи «счёт ↔ вариант» | DTO счёта | `cvar_invoice` |
| связи «отчёт о поставке ↔ вариант» | `document-supply-report` | `cvar_supply` |
| списка участников КП в запросе генерации | `offer-word/multi`, `build-offer-requests` | `cvar_offer` |
| правила «только вперёд» | сервис (`markStageForward`) | любая стадия при переделке |
| правила «что такое переделка» | вопрос к заказчику | откат стадий |

## API сервиса

```ts
const lifecycle = new ComplectVariantLifecycleService(bitrix, portalModel);

await lifecycle.markSuccess(domain, [5001, 5002]);
await lifecycle.markRejected(domain, [5003]);
await lifecycle.markStage(domain, [5004], COMPLECT_VARIANT_STAGE.OFFER);
```

Все методы возвращают `{ requested, moved, skipped }` и никогда не бросают на
отсутствие смарта/стадии — только на сбой самого HTTP-клиента Битрикса (его
вызывающий обязан ловить сам, шаг не критичен).

Сервис **не** `@Injectable`: внутри per-request `BitrixService` и `PortalModel`
конкретного портала — держать их в синглтоне нельзя (race condition между
доменами).
