# Airtime — эфирное время менеджеров

`POST /api/kpi-airtime/get` — суммарная длительность звонков (CALL_DURATION из
`voximplant.statistic.get`) по сотрудникам за период, с разбивкой
входящие/исходящие.

## Как считается (месячное партиционирование + кэш)

Период режется на календарные месяцы (`shared/lib/month-segments.util.ts`,
общий с sales-finance):

- **Прошлые полные месяцы** — из кэша ячеек «домен × сотрудник × месяц»
  (`AirtimeCacheService` поверх центрального `@lib/app-cache`: Redis +
  таблица `app_cache` в MySQL — переживает перезагрузку Redis). Промахи
  добираются **одной** voximplant-выборкой месяца по недостающим
  сотрудникам и кэшируются, включая **нулевые ячейки** (сотрудник без
  звонков) — иначе «тихие» сотрудники промахивались бы вечно.
- **Текущий месяц и неполные краевые сегменты** — всегда живой запрос,
  без кэша: сегодняшние данные меняются.

Ячейка — только агрегат (~120 байт): `{callsCount, airtimeSeconds,
incoming{count,seconds}, outgoing{count,seconds}}`. Сырые строки звонков
не хранятся.

### Почему per-user×month, а не по составам команд

Любой фильтр сотрудников и любой диапазон прошлых месяцев собирается из
одних и тех же ячеек — число ключей не растёт комбинаторно от фильтров.
Объём: портал на 100 сотрудников × 24 месяца ≈ 2400 ячеек ≈ **300 КБ**.

### Границы дат (важно)

Фильтры voximplant строгие (`>CALL_START_DATE`, `<CALL_START_DATE`).
Ячейка месяца канонична: `> 'yyyy-MM-01'` и `< первый день следующего
месяца`. Краевые сегменты запроса используют исходные dateFrom/dateTo —
суммарная семантика идентична прежней единой выборке. Дата с временем
(`...T12:00:00`) на краю периода делает краевой сегмент некэшируемым
(ячейка не умеет срез по часам).

Бонус: месячная выборка почти никогда не упирается в лимит строк (10k) —
`truncated` на длинных периодах лечится сам. Обрезанный месяц в кэш
**не** пишется.

## Как и когда чистится

| Что | Где лежит | TTL | Кто чистит |
|---|---|---|---|
| Ячейка прошлого месяца | Redis + `app_cache` | 180 суток (`AIRTIME_MONTH_TTL_SECONDS`) | Redis протухает сам; строки MySQL удаляет почасовой `purgeExpired`-cron `AppCacheService`. После протухания месяц пересчитывается при следующем запросе |
| Текущий/неполный сегмент | нигде | — | не кэшируется |
| Airtime внутри снимка публичной ссылки | Redis + `app_cache` (app `kpi-share`) | до `expires_at` ссылки (≤14 дней) | TTL + purge-cron; отзыв ссылки удаляет сразу |

### Ручной сброс («чтоб начал работать перезапрос»)

Точечная ручка `POST /api/kpi-airtime/cache/reset` (БД + Redis разом,
следующий запрос честно пересчитает задетые месяцы):

| Тело | Что сбрасывает |
|---|---|
| `{ "domain": "..." }` | все ячейки портала |
| `{ "domain": "...", "month": "2026-06" }` | месяц по всем сотрудникам |
| `{ "domain": "...", "userIds": [447, 11] }` | все месяцы указанных сотрудников |
| `{ "domain": "...", "month": "2026-06", "userIds": [447] }` | точечные ячейки |

Универсальная альтернатива: `POST /api/app-cache/reset { "app": "airtime",
"domain": "..." }`. Инспекция: `POST /api/app-cache/list { "app": "airtime" }` —
видно ячейки, `inRedis`, `expiredAt`.

## На что обратить внимание

- `AirtimeStatisticUseCase` — НЕ Injectable, создаётся
  `new AirtimeStatisticUseCase(bitrix.api, cache, domain)` per-domain
  (правило CLAUDE.md про race condition c this.bitrix).
- `AirtimeCacheService` — @Injectable (bitrix-состояния нет); в
  share-link-снапшоте создаётся вручную `new AirtimeCacheService(appCache)`.
- Чистая логика агрегации/слияния — `lib/airtime-cell.util.ts`
  (покрыта `__tests__/airtime-cell.util.spec.ts`).
- `rowsFetched` в ответе — только живые строки текущего запроса (ячейки из
  кэша строк не добавляют); `truncated` — если хоть один живой сегмент
  обрезан по лимиту.
