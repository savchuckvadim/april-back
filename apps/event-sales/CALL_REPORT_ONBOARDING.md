# Подключение портала к AI-анализу звонков — полная инструкция

Дата ревизии: 2026-08-23. Проверено по коду (аудит + адверсарная
верификация). Связанные документы: `CALL_REPORT_FLOW.md` (как работает
конвейер), `CALL_REPORT_SMART_FIELDS.md` (поля смарта),
`ai/tasks/sales-data-strategy-plan.md` (стратегия).

Сценарий документа: клиент УЖЕ пользуется другими нашими сервисами
(портал заведён в нашей БД), нужно включить ему AI-анализ звонков.

---

## 1. Чек-лист портала

### 1.1. В нашей БД (4 сущности)

| Что | Где | Зачем |
|---|---|---|
| строка `portals` с `domain` + рабочим ключом (`key`/`nestKey`) | заводится вне этого репо (Laravel online) | из него собирается вебхук `https://{domain}/{key}/{method}` |
| слепок портала из online-API (`getportal`) | кэш Redis `portal_{domain}`, TTL 10 ч | поля, воронки, списки, отделы |
| строка `portal_ai_settings` с `enabled=true` | админка → Портал → AI | **без неё портал не попадает в обход крона вообще** (env-списка доменов больше нет) |
| `vibeKey` портала | админка `PUT /admin/portal/:id/keys/vibeKey` | ЕДИНСТВЕННЫЙ источник ключа VibeCode (env-fallback выпилен) |

Создаются автоматически при установке смарта: строка `smarts`, зеркала
`bitrixfields` / `bitrixfield_items`. Рабочие таблицы `transcriptions`
(unique `dedup_key`) и `ais` — общие.

### 1.2. Права REST-ключа Bitrix

Вебхук должен быть создан **администратором портала** — иначе часть
методов молча падает.

- `telephony` — `voximplant.statistic.get` (поиск звонков);
- `crm` — `activity.list` / `activity.binding.add`, `deal.get`,
  `lead.get`, `company.get`, `contact.get`, `duplicate.findbycomm`,
  `timeline.comment.add`, `type.list/add/update`, `item.add/update/list`;
- `userfieldconfig` — `list` / `add` (**требует админ-прав**: без них
  Bitrix отвечает «Вы не можете просматривать настройки…», код это
  диагностирует и подсказывает пересоздать вебхук);
- `disk` — `disk.file.get` (скачивание записи разговора);
- `user`, `department` — фильтр отдела продаж;
- `lists` — `lists.element.get` (КПИ / ОП История; опционально).

### 1.3. В самом Bitrix

- **Телефония с записью разговоров.** Признак записи берётся из
  `activity.FILES`; звонок без файла пропускается (`skippedNoAudio`).
- **Звонки привязаны к СДЕЛКЕ или ЛИДУ.** Активности с владельцем
  КОНТАКТ или КОМПАНИЯ отбрасываются (`skippedNonDeal`) — это один из
  крупнейших фильтров охвата, проверьте на портале заранее.
- **Отдел продаж заведён** и его `bitrixId` записан через pbx-install —
  иначе фильтр ОП работает fail-open (анализируются звонки всех).
- **Смарт-процесс установлен**: `POST /call-report/install-smart {domain}`
  (идемпотентно). Тариф портала должен позволять смарт-процессы.
- Списки `sales_kpi` / `sales_history` **не обязательны**: без них
  теряются только привязки отчётности и кандидаты для сверки.

### 1.4. Наши ключи

- глобальные env: `GIGACHAT_API_KEY` (+ сертификат Минцифры),
  `YA_ACCESS_KEY_KEY_ID` / `YA_ACCESS_KEY_SECRET` / `YA_BUCKET_NAME` /
  `YA_FOLDER_ID` (Yandex SpeechKit для длинных звонков), `APP_SECRET_KEY`;
- per-portal: **только `vibeKey`** — на нём работают классификация,
  глубокий разбор, ревизор и сверка.

Колонки `portals.llmKey / llmBaseUrl / llmModelName` в схеме есть, но
потребителей в коде нет — «своя LLM клиента» пока не реализована.

### 1.5. Marketplace vs вебхук

Маркетплейс-путь приоритетен при активной строке `marketplace_installs`:
OAuth access_token с авто-refresh, без online-API. Для legacy-портала
ключ приходит из внешнего `getportal` и локально не достраивается —
вебхук должен быть корректно заведён на стороне Laravel.

## 2. Порядок подключения и проверка каждого шага

1. **Ключ и права.** Пересоздать вебхук от администратора → проверить:
   `POST /call-report/scan {domain, windowHours: 2, maxPerRun: 1}` —
   `found > 0` означает, что телефония читается.
2. **vibeKey** в админке → проверить: `POST /call-report/analyze
   {domain, activityId}` на любом звонке — должен вернуть разбор.
3. **Смарт**: `POST /call-report/install-smart {domain}` → карточка
   появляется в CRM; при ошибке прав см. п. 1.2 (`userfieldconfig`).
4. **Настройки в админке** (Портал → AI): `enabled=Включено`, пороги
   (см. раздел 4), список сотрудников при необходимости.
5. **Контрольный прогон**: `POST /call-report/scan` → в логах строка
   `Скан {domain}: найдено N, в очередь M, уже обработано K, не сделки X,
   без аудио Y, не ОП Z` — по ней сразу видно, какой фильтр съедает охват.
6. **База знаний**: залить методички (kind'ы `call-analysis-*`,
   `call-classify`) — без них разбор идёт по базовому промпту.

## 3. Ограничение по сотрудникам

### 3.1. Что есть сейчас

| Механизм | Семантика | Где |
|---|---|---|
| `salesOnly` | только сотрудники отдела продаж; **fail-open** (отдел недоступен/пуст → фильтр выключается) | настройки портала, дефолт `true` |
| `allowedUserIds` | **белый список** bitrix-id; применяется ПОВЕРХ `salesOnly` (логика И) | настройки портала, дефолт `null` |

- `allowedUserIds` — это **полноценный прод-фильтр**: крон читает его из
  БД на каждом тике. Слово «ДЕМО» в подписях админки и в комментариях —
  историческое (так начинали пилот), поведение от этого не меняется.
- Пустой массив `[]` эквивалентен `null` — фильтр выключен.
- **Чёрного списка (исключить сотрудников) НЕТ.** Ни поля, ни кода.
- `POST /call-report/analyze` (ручной разбор) настройки портала **не
  читает** — у него свой параметр `userId`. Через эту ручку белый список
  обходится.

### 3.2. Как задать «только эти трое» уже сегодня

Админка → Портал → AI → список сотрудников: `[111, 222, 333]`.
Если эти трое не все в отделе продаж — дополнительно `salesOnly=false`,
иначе сработает И-логика и часть выпадет.

### 3.3. Что нужно добавить для «исключить некоторых»

Целевая семантика (списки работают и вместе, и по отдельности):

```
включён = (белый список пуст ИЛИ id ∈ белый список)
          И (чёрный список пуст ИЛИ id ∉ чёрный список)
          И (salesOnly=false ИЛИ id ∈ отдел продаж)
```

Рецепт добавления поля `excludedUserIds` в JSON-колонку `settings`
(**миграция не нужна**) — 5 файлов бэка + 2 фронта:

1. `libs/portal-lib/store/ai-settings/portal-ai-settings.types.ts` —
   поле в `PortalAiSettingsRecord` + ключ в `EMPTY_PORTAL_AI_SETTINGS`;
2. `…/portal-ai-settings.prisma.repository.ts` — санитайзер в
   `toJsonSettings` (образец `toUserIds`), ветка в `toPrismaData`,
   строка в `toRecord`;
3. `…/dto/portal-ai-settings.dto.ts` — **три** правки: присваивание в
   конструкторе Response-DTO, объявление с `@ApiProperty`, поле с
   валидаторами в Update-DTO;
4. `apps/event-sales/src/call-report/services/call-report-settings.service.ts`
   — `DEFAULTS`, интерфейс `EffectiveCallReportSettings`, `merge()`;
5. потребитель: `CallReportScanOptions` + тело скана + проброс в
   `call-report.scheduler.ts` (иначе настройка мёртвая);
6. фронт: мета в `…/ai-settings/model/index.ts` + для списков правки
   в `PortalAiSettingsPanel.tsx`;
7. регенерация orval-клиента с живого admin (:3004).

**Ловушка тестов:** фикстуры `emptyPortalSettings()` и
`effectiveSettings()` — нетипизированные литералы, компилятор о новом
поле не напомнит.

## 4. Гарантия полноты: «все звонки этих сотрудников»

### Короткий ответ: НЕТ, сейчас не гарантировано.

Система «догоняет» звонки, пока они внутри окна поиска, но у неё нет ни
курсора, ни докачки, ни отчёта о пропущенных. Ниже — узкие места, каждое
теряет звонки молча.

| # | Узкое место | Последствие |
|---|---|---|
| 1 | **Кэп 500 строк на скан**, сортировка по возрастанию даты, фильтра по сотрудникам в запросе к Bitrix НЕТ | выборка обрезается по ВСЕМУ порталу до фильтров → чужие звонки вытесняют звонки нужных людей; режутся самые свежие |
| 2 | **Окно считается от «сейчас»** (`windowHours`, дефолт 25 ч), догона нет | простой сервиса/портала дольше окна = безвозвратная потеря |
| 3 | `maxPerRun` (дефолт 10) режет хвост скана | хвост подхватится следующим сканом, **только пока в окне** |
| 4 | Строка в БД создаётся при СТАРТЕ транскрибации, а не при постановке в очередь | звонок в очереди дедупу невиден: следующий скан «ставит» его снова и жжёт слот `maxPerRun` впустую |
| 5 | `status='done'` ставится в конце ТРАНСКРИБАЦИИ | если стадия анализа упала дважды — звонок навсегда `done` без разбора; repair-крона нет |
| 6 | Строгие операторы сравнения | звонок ровно 60 сек при пороге 60 **не попадёт** (ставьте 59) |
| 7 | Звонки по КОНТАКТУ/КОМПАНИИ отбрасываются | крупный структурный фильтр охвата |
| 8 | Запрос активности спит 1 сек на каждого кандидата | длинный скан выходит за лок (25 мин < тик 30 мин) → параллельные сканы |
| 9 | Дроп страницы Bitrix трактуется как «данных больше нет» | тихая недовыборка (в kpi-модуле этот же случай возведён в исключение) |

### Расчёт для сценария «3 сотрудника, от 60 сек»

- Крон тикает каждые 30 минут → до 48 сканов/сутки.
- Если `scanIntervalMinutes` **не задан** (дефолт) — скан на каждом тике:
  48 × `maxPerRun`. При `maxPerRun=10` это 480 звонков/сутки — запас есть.
- Если админ вписал `scanIntervalMinutes=60`, фактический период
  становится **90 минут** (отметка времени пишется ПОСЛЕ скана) → 16
  сканов → 160 звонков/сутки: при потоке 200 дефицит ~40/сутки, и они
  теряются, как только выпадут за окно.
- **Главный риск именно для порога 60 сек**: чем ниже порог, тем больше
  сырых строк по всему порталу — и тем вероятнее, что кэп 500 срежет
  звонки ваших троих ещё до фильтра.

### Что настроить прямо сейчас (максимум охвата на текущем коде)

| Настройка | Значение | Почему |
|---|---|---|
| `minDurationSec` | **59** | оператор строгий: 59 даёт «от 60 включительно» |
| `windowHours` | 48–72 | запас на простои (ручной скан принимает до 720) |
| `maxPerRun` | 50–100 | хвост не копится (в DTO ручки максимум 500) |
| `scanIntervalMinutes` | **не задавать** | скан на каждом тике = максимум слотов |
| `allowedUserIds` | ваши трое | |
| `salesOnly` | `false`, если кто-то из троих вне ОП | И-логика |

Плюс еженедельный ручной догон:
`POST /call-report/scan {domain, windowHours: 168, maxPerRun: 500,
userIds: [...], minDurationSec: 59}`.

### Что доделать в коде ради настоящей гарантии

По убыванию эффект/цена:

1. **Фильтр по сотрудникам на стороне Bitrix** (`PORTAL_USER_ID` в
   фильтре метода — в kpi-модуле уже реализован): снимает вытеснение
   кэпом 500. Для сценария «3 сотрудника» это решающая правка.
2. **Громкая обрезка**: возвращать признак обрезки и общее число,
   алертить; исключение на дроп страницы.
3. **Статус `queued`** — метка «занято» при постановке в очередь, а не
   при старте: чинит сгорание слотов и повторные запросы активности.
4. **Repair-крон**: строки `done` без записи разбора старше N часов →
   переставить стадию анализа (сейчас второго шанса нет).
5. **Отсев по строке статистики** (запись, тип сущности) до похода за
   активностью + убрать безусловную секундную паузу.
6. **Догон окна**: нижняя граница от `lastScanAt`, а не от «сейчас», с
   потолком (например 7 суток).
7. Лок крона длиннее тика; `staleMinutes` брать из настроек портала
   (сейчас редактируется в админке и ни на что не влияет).

## 5. GigaChat: где используется и что будет без него

### 5.1. Где используется

**Только «контур 1»** — первичный анализ: резюме + рекомендации.

- Заполняет **два поля смарта**: «Резюме GigaChat (RAG)» и
  «Рекомендации GigaChat»; пишет ais-записи `call-resume` /
  `call-recomendation` и коммент «AI-резюме звонка» в таймлайн сделки.
- Его резюме используется дальше как **фон**: история прошлых звонков в
  паспорте и fallback-выжимка в ночном ревизоре, если полного разбора нет.
- **Эмбеддинги GigaChat** питают векторный поиск (in-memory store,
  чанки 1000/200, top-k 2) — но только для kind'ов `resume` и
  `recomendation`.

### 5.2. Что работает НЕ на GigaChat

Классификация типа, глубокий разбор, три фокуса, синтез, ночной ревизор,
сверка по презентациям — **VibeCode/BitrixGPT** по `vibeKey` портала.
План-факт — вообще без LLM. Методички (`call-analysis-*`) читаются этими
разборами **полными текстами**, без векторного поиска.

### 5.3. Если GigaChat отключить

Конвейер **деградирует, а не падает** (покрыто тестом):

- транскрипт сохраняется, статус `done` ставится до всякой LLM;
- классификация, глубокий разбор, таймлайн разделов, смарт-элемент,
  ревизор и сверка — **работают**;
- пустыми останутся два поля GigaChat и коммент «AI-резюме» в сделке;
- ревизор потеряет fallback-выжимку для звонков без полного разбора.

Важные нюансы:

- один звонок = **от 1 до N** обращений: при транскрипте более 12 000
  символов идёт раздельный путь (2 вызова), при ошибке — ещё fallback;
  длинные диалоги дробятся map-reduce;
- при **пустой базе знаний** kind'ов `resume`/`recomendation` векторный
  поиск бросает исключение — контур 1 молча не даёт ничего даже при
  живом GigaChat (проверить в первую очередь, маскируется под «GigaChat
  не работает»);
- `llmModel='fake'` — **не выключатель**: провайдер возвращает
  правдоподобный выдуманный текст, который уедет в CRM. Чтобы уйти с
  GigaChat, ставьте `cloudru` / `openai` / `ollama`.

## 6. Переход на GigaChat для бизнеса

### 6.1. Зачем

- **Параллелизм**: физлицу официально доступен 1 поток (даже на платном
  пакете), юрлицу/ИП — 10 потоков по умолчанию, больше — по заявке на
  `gigachat@sberbank.ru`. Прямой выигрыш пропускной способности.
- **Юридически**: freemium физлица разрешён только для личного
  некоммерческого использования — эксплуатация в продукте требует
  бизнес-доступа.
- Контекстное окно (128 000 токенов у линейки GigaChat 2) от типа
  аккаунта **не зависит**.

### 6.2. Как подключить

1. Studio (`developers.sber.ru/studio`) → workspace **«Корпоративное»**
   (для постоплаты — «Корпоративное Плюс»).
2. Тип проекта **«GigaChat API Business»**.
3. Договор в doc/docx по ЭДО; в него вписывается **Account ID**
   (лицевой счёт) из письма о подключении или личного кабинета. Ответ
   менеджера — обычно 2 рабочих дня.
4. Ключ: проект → «Настройки API» → «Получить ключ». **Показывается один
   раз**, в кабинете не хранится. Это Base64 от `client_id:client_secret`.
5. Оплата: пакеты токенов (предоплата), счёт/оферта, либо pay-as-you-go
   (постоплата, минимальный месячный платёж 600 ₽; асинхронный batch —
   вдвое дешевле синхронного).

### 6.3. Что менять в приложении

**Код менять не нужно.** SDK читает настройки из env с префиксом
`GIGACHAT_`, а обёртки вычищают неуказанные поля — переменные окружения
долетают до клиента и для чата, и для эмбеддингов.

```env
GIGACHAT_API_KEY=<новый корпоративный ключ>
GIGACHAT_SCOPE=GIGACHAT_API_B2B     # или GIGACHAT_API_CORP (постоплата)
GIGACHAT_CONCURRENCY=10             # было 2 — по числу потоков юрлица
GIGACHAT_CA_PATH=/path/russian_trusted_root_ca.pem
# GIGACHAT_INSECURE_TLS — УБРАТЬ
# GIGACHAT_BASE_URL=https://api.giga.chat/api/v1   # см. ниже
```

**Критично:** без `GIGACHAT_SCOPE` SDK по умолчанию ходит как
`GIGACHAT_API_PERS` — корпоративный ключ получит ошибку авторизации.
Это самая частая ошибка перехода.

Прочее:

- OAuth: `POST https://ngw.devices.sberbank.ru:9443/api/v2/oauth`,
  заголовки `RqUID` (uuid4), `Authorization: Basic <ключ>`; токен живёт
  **30 минут** (одинаково для всех типов доступа); запросы за токеном —
  не чаще 10/сек.
- С 17.07.2026 основной адрес API — `https://api.giga.chat`; старый
  `gigachat.devices.sberbank.ru` работает для ранее подключённых. Дефолт
  SDK — старый адрес; при новом подключении уточните у менеджера, нужен
  ли переезд, и задайте `GIGACHAT_BASE_URL`.
- Сертификат НУЦ Минцифры обязателен (иначе `SELF_SIGNED_CERT_IN_CHAIN`,
  боевой инцидент 29.07.2026). Правильный путь — `GIGACHAT_CA_PATH` или
  `NODE_EXTRA_CA_CERTS`, не отключение проверки.
- Тарифицируются и промпт (включая системный), и ответ; ~3–4 символа на
  токен, точный подсчёт — `POST /tokens/count`.

### 6.4. Не подтверждено официально

RPS для эндпоинтов генерации (в документации лимит выражен в **потоках**,
