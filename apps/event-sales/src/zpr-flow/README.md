# zpr-flow — смарт «Звонки По решению» (ЗПР)

Сайд-поток event-sales: ведёт элементы смарт-процесса **«Звонки По решению»**
(`zpr_sales`) отдельной очередью ПОСЛЕ основного отчёта менеджера. Основной
flow (`event-report`) отвечает фронту «предварительно готово» сразу после
батча, а элемент смарта доезжает асинхронно и не удлиняет отчёт.

Зеркальный поток: [`../presentation-flow`](../presentation-flow/README.md) —
та же архитектура для смарта «Презентации».

---

## Бизнес-процесс словами

**Звонок по решению** — это звонок клиенту, у которого «дозрело» решение:
менеджер договорился созвониться в конкретный день и узнать итог. Каждый
такой звонок = ОДИН элемент смарта со своей историей.

Жизненный цикл элемента:

```
                    план (kind='plan')
                          │
                          ▼
                 ┌─ «Запланирован» ─┐ zpr_plan
        перенос  │                  │  отчёт (kind='report')
   ┌─────────────┤                  ├──────────────┬──────────────┐
   ▼             │                  ▼              ▼              ▼
«ЗПР: Перенос»───┘        «Состоялся: в работе»  «Состоялся:   «Не состоялся»
zpr_pending (открытая,     zpr_success            отказ»         zpr_noresult
элемент живёт дальше)      (дозвонились,          zpr_result_fail (не дозвонились)
                            работаем)             (дозвонились,
                                                   клиент отказал)
```

1. **План** (`kind='plan'`): менеджер запланировал ЗПР в отчёте → основной
   flow создал задачу Битрикса → этот поток создаёт элемент в
   «Запланирован» и привязывает его к план-задаче.
2. **Отчёт** (`kind='report'`): менеджер отчитался по ЗПР-задаче → поток
   находит элемент ЭТОЙ задачи и закрывает его стадией исхода
   (правило владельца 26.08: «дозвонились и получили отказ» ≠
   «не дозвонились» ≠ «дозвонились и работаем»).
3. **Перенос** (`kind='report', isMove`): отчёт «не очень» + та же задача
   на новую дату → элемент НЕ закрывается, двигается в «ЗПР: Перенос» с
   инкрементом счётчика переносов. Открытого элемента нет — план создаётся
   заново (с обеими анкетами: другого носителя у ответов не будет).
4. **Спонтанный**: отчитались, а открытого элемента нет (плана не было) →
   факт звонка фиксируется элементом сразу в закрытой стадии с
   `ZPR_IS_SPONTANEOUS='Y'`.

Стадия `zpr_fail` («Отменён») автоматикой НЕ проставляется — она для ручной
отмены плана менеджером; см. открытый вопрос в конце.

### История комментариев (требование владельца)

План-коммент при создании, отчёт-коммент при закрытии, запись о переносе —
всё дублируется в накопительную ленту `ZPR_COMMENTS` (обрезается до 50
записей, новые сверху).

## Как джоб попадает сюда

```
POST /event-sales/flow (фронт)
  └─ EventReportUseCase (основной батч: задача add_task, сделки, KPI…)
       └─ EventReportPostFlowService (../event-report/services/post-flow/)
            ├─ читает planTaskId из ОТВЕТА батча ($result[add_task] уже выполнен)
            ├─ собирает джобы билдером (side-flow-job.base.ts + zpr-flow-job.builder.ts)
            └─ queue.dispatch → EVENT_SALES_ZPR_FLOW
                 └─ ZprFlowProcessor (этот модуль)
                      └─ ZprFlowUseCase.handle(job)
```

На один отчёт может уехать ДВА джоба: `report` (закрыть текущий элемент) и
`plan` (создать следующий) — порядок постановки «сначала report» обязателен
и охраняется post-flow.

## Ключевые механики

### 1. Какой элемент закрывается: ПРИВЯЗКА ЗАДАЧИ, потом эвристика

Отчёт идёт по конкретной задаче, и задача ЗНАЕТ свой элемент: в её
`UF_CRM_TASK` лежит динамическая привязка `T{entityTypeId в hex}_{id}`
(её пишет наш `SideFlowTaskBinderService`).

Живой пример (инцидент 31.08): задача 741867 несла
`["L_330743", "D_25359", "CO_167075", "T424_15"]` → `0x424 = 1060` (наш
entityTypeId) → элемент **15**. Старая эвристика «самый свежий открытый
элемент клиента» закрыла не его, а завела спонтанный дубль — у клиента
может быть НЕСКОЛЬКО запланированных звонков, и эвристика тут в принципе
не может быть верной.

Порядок в [lookup](services/zpr-element-lookup.service.ts):

1. Привязки задачи (`job.taskCrmBindings`, кладёт post-flow из
   `currentTask` фронта) → парсер
   [`parseSmartElementIdsFromTaskBindings`](../../../../../libs/portal-lib/pbx/const-smart-registry/lib/smart-task-binding.ts)
   → `crm.item.get` каждого id → берём открытый. Слово задачи ФИНАЛЬНО:
   её элемент уже закрыт — честный `null` (→ спонтанный), БЕЗ отката на
   эвристику, иначе закрылся бы чужой план.
2. Эвристика по клиенту — только для легаси-задач без привязки: открытые
   стадии + совпадение ЛЮБОЙ из связей (сделка ИЛИ компания ИЛИ лид; не
   «первой заданной» — это был второй баг инцидента).

### 2. Три контура связи (см. links.builder)

| Контур | Поля | Зачем |
|---|---|---|
| Наши crm-поля | `ZPR_BASE_DEAL`, `ZPR_COMPANY`, `ZPR_LEAD`, `ZPR_CONTACT`, `ZPR_PRES_DEAL` | поиск элемента из кода |
| Родители | `parentId2/4/1/3` | вкладка дочерних элементов и штатный фильтр в карточке |
| Клиент | `companyId`, `contactIds` | блок «Клиент», телефония, письма (isClientEnabled='Y') |

### 3. Формат значения crm-поля зависит от НАСТРОЕК поля

Считает [`buildCrmLinkValue`](../../../../../libs/portal-lib/pbx/const-smart-registry/lib/crm-link-value.ts):
одиночное однотипное поле (все поля ЗПР) → **голый id** (`25359`);
мультитипное → префикс (`D_25359`); множественное → массив. Инцидент 31.08:
в одиночные поля уезжал `['D_25359']`, и Битрикс молча не сохранял связи.
Чтение (`hasCrmLink`) терпит ОБА поколения формата.

### 4. Идемпотентность — две независимых защиты

- постановка: детерминированный jobId `{operationId}:zpr:{kind}` (Bull
  молча не ставит дубль);
- доставка: [`SideFlowGuardService`](../shared/side-flow/side-flow-guard.service.ts)
  — `begin` до работы, `complete` после; повторная доставка выполненного
  джоба только повторяет WS-нотификацию.

### 5. Честные деградации (ничего не падает молча)

| Ситуация | Поведение |
|---|---|
| Смарт не установлен на портале | джоб «skipped»; есть ответы анкеты — WARN о потере |
| Закрывающей стадии нет (старая установка) | отчёт записан БЕЗ смены стадии + WARN |
| Поля нет на портале | значение пропущено (`setUf`) |
| `baseDealId` не приехал (сделка создавалась тем же батчем) | дотяжка по компании ([SideFlowBaseDealResolver](../shared/side-flow/side-flow-base-deal.resolver.ts)), только СВОИ сделки ответственного |
| Элемент из привязки задачи не прочитался (сеть) | WARN + ветка «открытого нет» (не чужой элемент!) |
| Ошибка привязки к задаче / обратной ссылки | WARN, джоб не падает — это украшения, не инварианты |
