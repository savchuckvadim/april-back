# Отчёт по дублям сделок (duplicate-report)

Раз в неделю крон находит **клиентов, у которых больше одной открытой сделки**
в воронке «ОП Основная» (sales_base), разбирает каждого — какую сделку
оставить основной, что присоединить, где решать руководителю, откуда взялся
дубль — и ставит получателям **задачу с Excel-отчётом**.

Модуль **только читает CRM и ставит задачи**. Сделки он не объединяет и не
двигает: присоединение делают люди (блок «Работа клиента» в «Звонках»),
потому что решение «чей это клиент» — управленческое, а штатное
«Объединить» Битрикса сливает дубли в одну карточку и удаляет их — отменить
нельзя.

> ⚠ Кнопка «Присоединить сюда» в «Возможных пересечениях» сделки ТОЙ ЖЕ
> компании не показывает (это окружение клиента, не дубль). Поэтому
> инструкция в задаче (`DUPLICATE_JOIN_HOW`) ведёт в блок «Работа клиента» —
> **включать задачи только после выкладки этого блока** (план
> ai/tasks/2026-10-01-day-plan.md, п.2).

Основа — разовый разбор garant 30.09.2026
(`ai/tasks/2026-09-30-duplicate-deals-report.md`, `…-duplicate-deals.xlsx`):
правила перенесены без привязки к порталу — ни id воронки, ни дат перегона,
ни сотрудников в коде нет.

## Как разбирается клиент

Клиент — компания сделки; у сделок без компании — контакт. Сделка без
компании, чей контакт стоит в сделке ровно одной компании, относится к этой
компании (повторная заявка, узнанная только по контакту); контакт в сделках
двух компаний — неоднозначно, остаётся у контакта. Дубль — клиент с
двумя и более открытыми сделками воронки (после исключения сотрудников из
настройки «не включать сделки сотрудников»).

| Что | Правило |
|---|---|
| **Основная** | очки: работающий ответственный (главное) → дальше по воронке (порядок `PBX_DEAL_SALES_BASE_STAGES`) → есть сумма → нормальное название (не пустое, не «Сделка #N», не ИНН) → открытые задачи (до 5, только развести равных). Равенство — более свежая по `DATE_MODIFY`, затем меньший ID |
| **Самая свежая** | максимальный `DATE_MODIFY`, равенство — больший ID: к ней присоединится новая заявка клиента. Компаратор общий с входом повторной заявки (`shared/lead-request/deal-freshness.util`) |
| **Ведёт сам** (сделка) | у ответственного свои открытые задачи по сделке или своё дело (`LAST_ACTIVITY_BY` = ответственный) не старше 30 дней. **Не** `DATE_MODIFY`: её сдвигают роботы и наша автоматика, в т.ч. аудит сделок (проба garant 01.10: изменение — пользователь 1, последняя активность почти везде — владелец вебхука 447); чужие задачи по сделке не в счёт |
| **Ведут как одного** | одна открытая задача привязана к двум сделкам клиента — спора нет |
| **Решить руководителю** | двое и больше РАБОТАЮЩИХ ответственных, и каждый ведёт свою сделку сам (и не «ведут как одного»); либо у сделок разные ИНН (`op_inn`) — в задаче «проверить ИНН», до проверки не присоединять |
| **Присоединить к основной** | всё остальное |
| **Как появилась** (каждая сделка, кроме самой старой) | сделка из лида старше суток, созданная в те же сутки, что другая сделка клиента из лида, — «несколько лидов стали сделками разом» (перенос 15–18.09, массовая обработка); лид-источник моложе первой сделки клиента — «новая заявка»; старше — «старый лид отправлен в работу»; без лида и без названия или создана владельцем вебхука — «автоматика»; без лида, создал сотрудник — «заведена вручную». У клиента — как появилась самая молодая сделка |
| **Новое за неделю** | самая молодая сделка создана в периоде: с начала первого дня до начала дня отчёта (ночная заявка дня отчёта — в следующем) |
| **Все ответственные не работают** | после присоединения нужно назначить работающего |

Лид-источник — наше поле `deal_from_lead_id`, иначе штатный `LEAD_ID`.
«Работает» — `ActiveStaffService`: аккаунт активен и не в отделе
неработающих. Все коды полей и воронки — из реестров pbx и `PortalModel`
(ai/rules/pbx-typing.md).

## Кому уходит отчёт

Правила — как у сводок аудита сделок (`deal-audit`), общий код в
`shared/department-heads`:

- **«Отчёт РОПу»** — руководителю отдела по структуре (снимок `bx-department`,
  с подъёмом по PARENT, если у отдела руководителя нет): клиенты, у которых
  хоть одна сделка на его сотруднике;
- **«по своему отделу — кому»** — отдел получателя и все подотделы
  (`departmentScopeOf`);
- **«по всей структуре — кому»** — все клиенты портала.

Человек в нескольких списках получает **одну** задачу с объединённым
набором. Неработающим получателям задача не ставится (предупреждение в
Telegram). Клиенты, которых никто не получил (все ответственные уволены или
вне отдела продаж — в снимке структуры их нет), при «Отчёте РОПу» уходят
**руководителям верхних отделов продаж** (родителя нет в снимке, роль
`orphan`); без «Отчёта РОПу» — только строка в Telegram «клиентов без
получателя: N».

## Настройки (админка → Settings → event-sales)

| Настройка | Дефолт | Что делает |
|---|---|---|
| Отчёт по дублям сделок: включён | **выкл** | рубильник крона на портале |
| день недели (1–7) | 1 (пн) | день отчёта по TZ портала |
| час отправки (0–23) | 9 | с какого часа в этот день |
| только считать | **вкл** | итог только в Telegram: ни файлов, ни задач |
| руководителю отдела (РОПу) | вкл | см. «Кому уходит отчёт» |
| по своему отделу — кому | — | Bitrix ID через запятую |
| по всей структуре — кому | — | Bitrix ID через запятую |
| не включать сделки сотрудников | — | Bitrix ID: их сделок нет в отчёте вовсе |
| срок задачи (рабочих дней) | 3 | конец N-го рабочего дня по календарю портала, считая день отчёта |

**Чтобы задачи пошли**: «включён» — вкл, «только считать» — выкл, хотя бы
один получатель. Webhook должен иметь scope `disk` (файл) и `task`.

## Расписание

Тик крона — каждый час (`event-sales-duplicate-report`). Портал прогоняется,
когда по его TZ наступили день и час отчёта (или позже на этой неделе — бэк
лежал в понедельник, отчёт уйдёт во вторник) и отчёт этой недели ещё не
уходил. В дни догона час тоже проверяется — ночью задач не будет.

Состояние — `DuplicateReportRunState` (Redis):

- метка недели `event-sales:duplicate-report:last-week:{domain}` (у «только
  считать» своя, `last-week-count:` — выключили «только считать» в ту же
  неделю, задачи уйдут при ближайшем тике). Ставится только после
  **доставки**: «только считать», получателей нет или хоть одна задача
  поставлена. Ноль задач из N — сбой, неделя открыта;
- сбои недели `event-sales:duplicate-report:failed:{domain}` = `неделя:N`:
  прогон повторяется каждый тик, в Telegram — первый сбой и пятый
  (`DUPLICATE_REPORT_MAX_ATTEMPTS`), после него неделя закрывается;
- лок `event-sales:duplicate-report-lock` — с токеном владельца
  (compare-and-delete), продлевается перед каждым порталом; общий с ручкой.

Неполный ответ batch (упал целый чанк) роняет прогон (`strict`) — он
повторится, а не уйдёт с искажёнными задачами. Тики, где все ждут своего дня
или молча повторяют сбой, — только в лог.

Это **крон-задача, а не эндпоинт с данными для UI**: паттерн «очередь + WS +
Redis-кэш» (ai/rules/heavy-endpoint-queue.md) здесь не нужен — результат
никто не ждёт в браузере, он уходит задачей и в Telegram.

## Ручка

```
POST /duplicate-report/run-now
{ "domain": "example.bitrix24.ru", "dryRun": true }
{ "domain": "example.bitrix24.ru", "previewUserId": 1 }
```

Прогон сейчас — вне расписания и независимо от «включён». `dryRun: true` —
только посчитать, `false` — поставить задачи даже при включённом «только
считать», не указан — по настройке. Идёт в фоне, ответ сразу
(`{ started, message }`), итог — в Telegram. Прогон с задачами закрывает
неделю (крон не повторит его следом), «только посчитать» — нет.
`previewUserId` — **проба**: весь отчёт портала одной задачей этому
сотруднику (даже при «только считать»), остальным ничего, их прошлые задачи
не трогаются, неделя не закрывается.

## Доставка

1. Файл (`DuplicateReportDisk`) — в папку «Отчёты по дублям сделок»
   **личного Диска владельца вебхука**: `user.current` →
   `disk.storage.getList` (ENTITY_TYPE `user`, ENTITY_ID) →
   `disk.storage.getChildren` по имени, нет — `disk.storage.addFolder` →
   `disk.folder.uploadFile`. Имя — «Дубли сделок 28.09-04.10 — Имя
   получателя.xlsx». Папку не создать — файл в корень Диска.
2. Задача `tasks.task.add`: «Дубли сделок: отчёт за неделю 28.09–04.10»,
   ответственный — получатель, постановщик — владелец вебхука, срок — по
   календарю портала, описание в BB-коде (цифры, первые 10 клиентов
   таблицей со ссылками, что делать, предупреждение про «Объединить»),
   файл приложен при создании: `UF_TASK_WEBDAV_FILES: ['n' + id]`.
   К CRM задача **не привязана** — иначе сбила бы менеджеров и счётчик
   открытых задач аудита сделок.
3. Прошлая задача-отчёт получателя (`event-sales:duplicate-report:task:{domain}:{userId}`,
   90 дней) закрывается `tasks.task.complete` **после** создания новой.
4. Тем, кому отчёта в этот раз нет (дубли разобраны, убрали из настроек,
   перестал быть руководителем), прошлая задача закрывается тоже —
   множество получателей `event-sales:duplicate-report:recipients:{domain}`.
   Только если рассылка состоялась или дублей на портале нет вовсе: сбой
   Битрикса живые задачи не закрывает. Проба одному не закрывает ничего.

Любой сбой — предупреждение, а не падение: нет Диска — задача без файла,
не создалась задача одному — остальные получают.

## Архитектура

```
DuplicateReportScheduler (@Cron час) ── DuplicateReportRunState (лок, метки, сбои)
   │ ростер: portal_app_settings (duplicate_report_enabled)
   ▼
DuplicateReportSettingsService ──► DuplicateReportOptions
   ▼
DuplicateReportService.runForDomain                 ← её же зовёт ручка
   ├── DuplicateReportCollector
   │     ├── DuplicateDealsReader    все открытые сделки sales_base (deal.all)
   │     ├── groupDealsByClient / excludeOwners      (lib, чистые)
   │     ├── DuplicateContextReader  компании, контакты, лиды, задачи — 1 очередь batch
   │     ├── ActiveStaffService      кто работает
   │     └── classifyClients         (lib, чистые)
   ├── assignRecipients              (lib, чистые) + структура bx-department
   └── DuplicateReportDispatcher     имена, срок, Excel, DuplicateReportDelivery
                                     (DuplicateReportDisk — папка и файл)
```

Нет `this.bitrix` в `@Injectable`: инстанс по домену из `PBXService`,
читатели и доставка создаются `new` на прогон (CLAUDE.md).

## Отладка

- Крон молчит → портал не включён, не наступили день/час по TZ портала или
  метка недели уже стоит (`event-sales:duplicate-report:last-week:{domain}`)
  или прогон молча повторяет известный сбой (`…:failed:{domain}`).
  Не ждать — `POST /duplicate-report/run-now` с `dryRun: true`.
- Посмотреть отчёт глазами руководителя, никого не трогая — `run-now` с
  `previewUserId`.
- «получателей было бы: 0» → не задан ни один получатель или структура
  отдела продаж не прочиталась (warning).
- Задачи без файла → нет scope `disk` у вебхука или не найден личный Диск
  владельца (warning).
