# Аудит сделок (deal-audit) — поиск «забытых»

Крон обходит открытые сделки воронки «ОП Основная», считает **признаки
забытости** и записывает их в карточку полями `op_audit_*`, чтобы забытая
работа искалась штатным фильтром CRM и годилась как вход для роботов.

Модуль **только размечает**. Он не двигает стадии, не создаёт задач и не
ставит звонков: действия по забытым сделкам умеют делать хуки ОП
(`sales-hooks/`, `cold-hook-v2/`) — идемпотентно и с подстраховкой. Смешать
разметку с действиями значило бы получить крон, который сам себе создаёт
активность и потом считает её работой менеджера.

## Что считается признаком

| Признак (`op_audit_flags`) | Когда ставится | Порог из админки |
|---|---|---|
| Без открытых задач | по сделке и её компании нет ни одной открытой задачи | — |
| Просрочена задача | дедлайн открытой задачи прошёл дольше порога | «часов просрочки» (24) |
| Задача без дедлайна | задачи есть, но **ни у одной** нет срока | — |
| Нет даты следующего звонка | `call_next_date` пуст | — |
| Дата следующего звонка в прошлом | `call_next_date` < сейчас | — |
| Давно нет работы | `LAST_ACTIVITY_TIME` старше порога | «дней без работы» (14) |
| Застряла в стадии | `MOVED_TIME` старше порога | «дней в стадии» (30) |
| Забыли закрыть | стадия из предпродажных и тишина дольше порога | «дней до забыли закрыть» (21) |
| Нет ответственного | `ASSIGNED_BY_ID` пуст | — |

Предпродажные стадии для «забыли закрыть»: `sales_document_send`,
`sales_in_progress`, `sales_money_await`, `sales_supply`. «Презентация» и
«Доработка» сюда НЕ входят — там пауза законна (ждём реквизиты, согласуем
дату), и признак давал бы ложную тревогу.

## Почему признаков ДВА поля

- `op_audit_status` — **один худший** признак. По нему строится фильтр
  канбана («покажи забытые») и условие робота: робот умеет сравнивать одно
  значение, а не разбирать множественное поле.
- `op_audit_flags` — **все** сработавшие признаки. Сделка бывает
  одновременно без задачи, застрявшей и с просроченной задачей; одного
  значения для разбора «почему» не хватает.

Приоритет статусов (от худшего): забыли закрыть → без задач → просрочена
задача → давно нет работы → застряла. Обоснование порядка — в
`constants/deal-audit.const.ts`.

Числа рядом (`op_audit_idle_days`, `op_audit_overdue_days`,
`op_audit_stage_days`, `op_audit_open_tasks`) нужны не для красоты: фильтр
CRM умеет «больше N» по числу и не умеет по enum-признаку.

## Поля сделки (установка на портале)

Все — **только сделка**, все пишет крон.

| Код | Тип | Смысл |
|---|---|---|
| `op_audit_status` | enumeration | худший признак |
| `op_audit_flags` | enumeration, multiple | все признаки |
| `op_audit_at` | datetime | когда посчитали |
| `op_audit_idle_days` | integer | дней без активности |
| `op_audit_overdue_days` | integer | дней просрочки самой старой задачи |
| `op_audit_stage_days` | integer | дней в текущей стадии |
| `op_audit_open_tasks` | integer | открытых задач по сделке и компании |
| `op_audit_comment` | string | расшифровка по-русски |

Зеркало реестра — `PBX_SALES_EVENT_FIELDS` (`appType: 'audit'`). Источник
установки — `storage/app/install/sales/entity-fields/data.xlsx`, лист
`calling_fields` (+ `fieldsItems` для справочников). **Строки в шаблон ещё
не внесены** — см. задачу `ai/tasks/2026-09-15-deal-audit-cron.md`.

Пока полей нет, модуль работает как **self-gate**: считает, пишет warning
«поля аудита не установлены» и **не размечает карточки**. Сводки при этом
рассылаются: они собираются из вердиктов прогона и в поля карточки не
смотрят (`lib/deal-audit-run-mode.ts`). Раньше рассылка шла только вместе с
записью, и портал без полей не получал оповещений вовсе.

## Настройки (админка → Settings → event-sales)

| Настройка | Дефолт | Что делает |
|---|---|---|
| Аудит сделок: включён | **выкл** | рубильник крона на портале |
| Интервал (минут) | 1440 | как часто аудировать портал |
| Только считать (не писать) | **вкл** | холостой ход: считаем, но не пишем и не рассылаем |
| Лимит за прогон | 500 | сколько карточек размечать за тик |
| Дней без работы | 14 | порог признака «давно нет работы» |
| Часов просрочки задачи | 24 | запас, чтобы «на сегодня 18:00» не считалось просрочкой |
| Дней в одной стадии | 30 | порог «застряла» |
| Дней до «забыли закрыть» | 21 | порог тишины на предпродажных стадиях |
| Сводку сотруднику | выкл | менеджеру — его забытые сделки |
| Сводку РОПу | выкл | руководителю отдела по структуре — сделки его сотрудников |
| Сводка по своему отделу — кому | — | Bitrix ID: сделки сотрудников своего отдела и всех подотделов (свой — где числится или которым руководит); для тех, кто не отмечен руководителем в структуре |
| Сводка по всей структуре — кому | — | Bitrix ID: общая сводка по всем отделам, подчинённые не нужны |
| Не включать в сводки сделки сотрудников | — | Bitrix ID: тестовые, руководство — их сделок нет ни в одной сводке (разметка карточек остаётся) |
| Строк в сводке | 20 | остаток сворачивается в «и ещё N» |

**Чтобы оповещения пошли**, нужны три настройки разом: «Аудит сделок:
включён» — вкл, «Только считать» — выкл, и хотя бы один получатель
(«Сводку сотруднику», «Сводку РОПу», «Сводка по своему отделу» или
«Сводка по всей структуре»). Установленные поля для этого не нужны.
Сводка уходит, только если забытые сделки нашлись.

Частота **тика** крона фиксирована (30 минут), частота аудита **портала** —
настройка: тик фильтрует домены по Redis-метке последнего прогона. Так
частоту меняют из админки без деплоя (паттерн `skap-import.scheduler`).

## Ручка

```
POST /deal-audit/run
{ "domain": "example.bitrix24.ru", "dryRun": true, "maxDeals": 50, "dealIds": [1234] }
```

Возвращает ПОЛНЫЙ разбор прогона: сколько проверено, сколько забытых,
разбивку по статусам и сами сделки с расшифровкой. Нужна для обкатки —
посмотреть, кого крон пометит, ДО включения записи на живом портале.
`dealIds` отвечает на вопрос «почему вот эта сделка помечена забытой».

Выполняется синхронно: на большой воронке ответ занимает десятки секунд
(на garant — дольше таймаута прокси, ответ не доходит).

```
POST /deal-audit/run-now
{ "domain": "example.bitrix24.ru" }
```

Прогон «как у крона» прямо сейчас, вне интервала, по настройкам портала:
разметка и сводки — по-настоящему. Идёт в фоне, ручка сразу отвечает
`{ started: true }`, итог приходит в Telegram тем же отчётом, что у крона.
Лок общий с кроном (идёт другой прогон — `started: false`), метка
последнего прогона обновляется — крон не повторит прогон следом.

## Архитектура

```
DealAuditScheduler (@Cron 30 мин, Redis-лок)
   │ ростер: portal_app_settings (app=event-sales, deal_audit_enabled)
   │ интервал per-портал: Redis-метка последнего прогона
   ▼
DealAuditSettingsService ──► DealAuditOptions (пороги + режим + дайджест)
   ▼
DealAuditService.runForDomain(domain, options)     ← её же зовёт ручка
   ├── DealAuditTasksReader   открытые задачи портала → индекс по D_/CO_
   ├── DealAuditDealsReader   открытые сделки sales_base → слепки
   ├── evaluateDeal()         ЧИСТЫЕ правила (lib/deal-audit-rules.ts)
   ├── DealAuditWriterService batch-запись op_audit_* (только изменившиеся)
   └── DealAuditDigestService сводки: менеджеру / РОПу / по своему отделу
                              (lib/deal-audit-department-scope.ts) / по всей
                              структуре; минус исключённые сотрудники
```

Ключевые решения:

- **Задачи читаются один раз на прогон**, а не по задаче на сделку: тысяча
  сделок — это тысяча вызовов `tasks.task.list`, что не проходит по лимитам
  REST. Первая страница синхронно, остальные — батчами по 50 смещений.
- **Задачи компании учитываются**: холодный обзвон ставит задачу на
  КОМПАНИЮ, а работа идёт по сделке. Без этого сделка в работе выглядела бы
  «без задач».
- **Пишутся только изменившиеся статусы**: прогон ежедневный, иначе история
  карточки за месяц обрастает тридцатью одинаковыми правками.
- **Правила — чистая функция** без Битрикса и без `Date.now()` внутри: вся
  содержательная логика покрыта тестами без сети и портала.
- **Нет `this.bitrix` в `@Injectable`** — инстанс берётся по домену через
  `PBXService`, доменные сервисы создаются `new` на вызов (CLAUDE.md).

## Отладка

Крон сам пишет в Telegram (через логгер, `{ telegram: true }`):

- **при старте event-sales** — общий список кронов приложения с
  ближайшими запусками (`CronJobsReportModule` из `@lib/core/schedule`) и
  отдельно, на каких порталах включён аудит и в каком режиме («только
  считать», «получатели не заданы», интервал);
- **после тика, где хоть один портал прогнан или упал** — строка на
  портал: сделок, забытых, размечено, сводок, предупреждения. Тики, где
  все порталы ждут интервала, идут только в обычный лог.

- Крон молчит → в `portal_app_settings` нет портала с
  `deal_audit_enabled: true`, либо не прошёл интервал (ключ Redis
  `event-sales:deal-audit:last-run:{domain}`; метку ставит и прогон в
  режиме «только считать»). Не ждать интервала — `POST /deal-audit/run-now`.
- Прогон есть, карточки пустые → warning «поля аудита не установлены» либо
  включена настройка «только считать». Сводки при неустановленных полях
  всё равно уходят — в ответе ручки это поле `digestSent`.
- Все сделки помечены забытыми → пороги в админке слишком жёсткие; прогнать
  ручку с `dryRun: true` и посмотреть `byStatus`.
- Сводки не приходят → аудит выключен, включено «только считать», не задан
  ни один получатель либо забытых сделок нет; для «Сводки РОПу» и «по
  своему отделу» дополнительно нужна прочитанная структура отдела продаж
  (warning «структура отдела продаж не прочитана»). На garant структура —
  мультирежим «(ОП)»: с 30.09.2026 снимок отдела включает ОП, их группы и
  предков (`@lib/bx-department`).
