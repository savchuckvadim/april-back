# Реанимация отказников (reject-revive)

Крон раз в час возвращает отказные сделки основной воронки (стадии
`sales_fail` / `sales_double` / `sales_not_ca`) в работу: ставит холодный
звонок существующим cold-call хуком (`ColdHookSilinceEndpointService` —
внутренний вызов, тот же silence-буфер, что у БП-хука).

## Когда сделка — кандидат

- прошло `reject_revive_interval_days` дней с закрытия (`CLOSEDATE`), ЛИБО
- (при `reject_revive_use_post_fail_date`) наступила «ОП Дата звонка после
  отказа» (`post_fail_date`) — она перебивает интервал; сделка с заполненной
  датой в интервальную ветку НЕ попадает.

## Двухфазная подстраховка (переживает падение хука)

1. `op_xo_revive_queued_at` ставится ДО отправки хука — устойчивый маркер
   «ожидает исполнения» прямо на сделке в Битриксе;
2. хук принят буфером → `op_xo_revive_sent_at`.

Падение между шагами оставляет сделку «недоехавшей»: следующий тик находит
такие (queued старше `reject_revive_resend_after_minutes`, sent пуст) и
досылает — фаза A, идёт ПЕРВОЙ и делит общий лимит `max_per_run` с фазой B.

Окно двойной задачи ровно одно: хук принят, а запись `sent_at` упала — тогда
досылка продублирует звонок. Принято by design: потерять клиента дороже.
`sent_at` означает «принято буфером», не «задача создана» — асинхронный отвал
внутри cold-hook виден его собственной телеметрией.

## Назначение

`reject_revive_assign_mode`: `same` — ответственному сделки; `random` —
случайному активному сотруднику отдела продаж из слепка портала
(`portal.departament`, group=sales); пустой отдел → фолбэк на `same` c
warning. Дедлайн звонка — завтра 10:00 локали портала.

## Повторный цикл

Новый отказ по сделке чистит оба маркера (`SalesBaseDealService.failFields`)
и пишет свежую `post_fail_date` — клиент реанимируется снова через интервал.

## Включение на портале

1. Установить поля сделки: `post_fail_date` («ОП Дата звонка после отказа»,
   date), `op_xo_revive_queued_at`, `op_xo_revive_sent_at` (datetime) — без
   маркер-полей фича молчит (self-gate);
2. админка → Settings → event-sales → «Реанимация отказников» + интервал/
   режим/лимиты.

## Отклонённые альтернативы

- **Стадия-очередь `sales_xo_await`** (order 15): видимая менеджерам очередь,
  но требует install стадии на всех порталах, повторно ОТКРЫВАЕТ закрытую
  сделку (CLOSED=N → сделка попадает в SLA-проход по сделкам и ломает
  эвристики «после WON_ORDER = отказ»). Маркер-поля закрытую сделку не
  трогают. Решение владельца: «может и не стадия, а просто поля».
- **Стадии-очереди в ЛИДЕ для отправки в ХО** — РЕАЛИЗОВАНО отдельно
  (todo2508 №3, стадия `lead_xo_queue` «Очередь в ХО», PBX_XO_QUEUE):
  страховка входа заявок ставит её ДО отправки хука и подбирает застрявших
  в ней ВНЕ окна создания — по полям такой лид уже никогда бы не нашёлся.
  Подробности — `lead-request/intake/lead-intake-rescue.service.ts`. У лида
  это работает без риска: он не «закрывается», в отличие от сделки.
  Порталы с похожим статусом сопоставляют его в админке вместо создания.
