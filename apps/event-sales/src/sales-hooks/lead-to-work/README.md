## ⭐ Аксиома процесса заявки (2026-08-10, от неё строим всё)

**Жизненный цикл заявки заканчивается в момент обнаружения компании.**

```
Появилась → Назначена менеджеру (ХО-хук) → Принята (менеджер, /accept)
    → работа: звонки/презентации (СОБЫТИЯ Звонков, не стадии)
    → ОБНАРУЖЕНА КОМПАНИЯ = финал квалификации заявки
```

В момент обнаружения компании по лиду становится точно известно и
фиксируется ИСХОД (маркеры уже существуют):

| Исход | Поле |
|---|---|
| Присоединился к существующей работе | `op_lead_is_merged_by_exist` |
| Стал инициатором продажи | `op_lead_is_boost_sale` + `to_sale_deal` |
| Дошёл только до презентации | `to_presentation_sales` |
| Не ЦА | `op_lead_not_ca_type` (+ Брак) |
| Отказ | fail-причины |

После этой точки лид не двигается — жизнь продолжается в компании и
сделках, лид носит исходы и историю обработки.

**Назначение ≠ принятие**: хук ставит «Назначена менеджеру»
(`lead_assigned`, site_stage «Назначена менеджеру»), принятие менеджером —
`POST /lead-request/accept` (кнопка в Звонках или робот стадии): стадия →
«Взята в работу», `op_lead_firstprepare_long` = секунды от назначения до
принятия (по истории), запись в историю. После передачи другому менеджеру
заявку нужно принимать заново.

## 1. Три режима использования (одним хуком)

> Отдельного «хука конвертации» НЕТ и не нужно: конвертация и ХО — это один
> use-case с разными флагами. 90% работы у них общая (чтение контекста,
> инвариант «одна пара», связи графа, задачи, ответственный), различия
> сведены во флаги — см. таблицу «Конвертация vs ХО» ниже.

### Режим A. «Перевод в работу» — переезд лида на сделку (КОНВЕРТАЦИЯ)

Заявка обработана, менеджер начинает вести клиента в воронке ОП.

```
stageMode=from_lead, isXo=N, taskMode=move
```

URL робота (на смену стадии лида, которая означает «пора в работу»):

```
POST {backend}/api/sales-hooks/lead-to-work/webhook
    ?leadId={{ID}}
    &stageMode=from_lead&isXo=N&taskMode=move
```

`responsible` здесь передавать НЕ нужно: конвертация не перераспределяет
работу — ответственный берётся с самого лида (`assigneeSource='lead'`).
Передавайте его только когда работу сознательно отдают другому человеку.

Что делает: создаёт основную сделку ОП (стадия — зеркало стадии лида, см.
§3), связывает её с лидом, переносит открытые задачи с префиксом «Звонок»,
двигает статус лида. ХО-сделку НЕ создаёт, ничего не закрывает.

#### Конвертация vs ХО: чем отличается

| Что | Конвертация (`isXo=N`) | ХО (`isXo=Y`) |
|---|---|---|
| ХО-сделка | не создаётся | создаётся (или передаётся существующая) |
| Стадия основной сделки | зеркало стадии лида (`from_lead`) | «Новая» (`new`) или «Холодная» (`cold`) |
| Задачи | переносятся с префиксом «Звонок» | закрываются, ставится «Холодный обзвон …» |
| KPI/History | **не пишутся** | «Запланирован» (+ «Не состоялся» прежнему при передаче) |
| Событийные поля ХО (`xo_date`, `op_history`…) | не пишутся | пишутся на лид, компанию и обе сделки |
| Метки заявки (`op_lead_site_*`) | не ставятся | ставятся при первом назначении |
| Подтверждение принятия | **не требуется** | требуется (`op_lead_assigned_at`, блокировка в «Звонках») |
| Переназначение ответственного | нет (работа остаётся у текущего) | да — лид, компания и сделки переходят новому |
| Уведомление менеджеру | только если ответственный сменился | всегда (с требованием подтвердить) |

Связи графа (`to_base_sales`, `deal_from_lead_id`, `deal_joined_leads`) и
инвариант «одна открытая пара» работают ОДИНАКОВО в обеих ветках.

#### Как проверить конвертацию

1. Взять лид, у которого ещё нет нашей сделки.
2. Дёрнуть URL выше (Swagger `/run` или робот).
3. Ожидаемо: появилась одна сделка ОП в зеркальной стадии; в сделке
   заполнены «Лид из которого создана» и «Присоединённые лиды»; в лиде —
   «Корневая сделка Продажи» и «Статус Лида»; открытые задачи получили
   префикс «Звонок»; **ХО-сделки нет, KPI пусто, подтверждения не просят**.
4. Повторный запуск по тому же лиду: вторая сделка НЕ создаётся (reuse),
   лишние открытые сделки уходят в fail — в логе `[consolidate]`.

#### Второй путь конвертации: штатная кнопка Битрикса

Если менеджер конвертирует лид штатной кнопкой Битрикса, сделку создаёт сам
Битрикс — наш хук в этом не участвует, и связи графа остаются пустыми. Для
этого случая есть отдельный вебхук-нормализатор (робот воронки СДЕЛОК, на
создание сделки):

```
POST {backend}/api/sales-hooks/convert-normalizer/webhook?dealId={{ID}}
```

Он self-healing дописывает `deal_from_lead_id`, `deal_joined_leads` и
`to_base_sales` лида по штатному `LEAD_ID` сделки; если у лида уже была наша
сделка — отдаёт warning «кандидат на merge». Стадии, задачи и KPI он не
трогает: это только починка связей.

### Режим B. «Холодный обзвон | Холодный обзвон. Заявка» — ХО из лида

Лид холодный, нужен цикл обзвона с аналитической ХО-сделкой.

```
stageMode=cold, isXo=Y, taskMode=close
```

Что делает: создаёт основную сделку ОП в стадии «Холодная» + ХО-сделку,
закрывает старые задачи и ставит новую «Холодный обзвон …», пишет KPI
«Холодный звонок Запланирован» (см. §6). Если лид распознан как **заявка**
(см. §7.1) — названия становятся «Холодный обзвон. Заявка. {Название}» /
«Холодный звонок Запланирован. Заявка. {Название}».
**Отличие от классического ХО-хука:** смежные сделки компании не
закрываются, компания не обнуляется — прошлое сохраняется.

#### Повторный ХО по лиду = передача обзвона

Если по лиду уже есть наша работа (сделки + задача «Холодный обзвон»),
повторный запуск с `isXo=Y` ведёт себя как классический ХО — «закрыть,
сбросить, передать»:

- открытые задачи закрываются, новая «Холодный обзвон …» — на нового
  ответственного;
- лид, компания, основная и ХО-сделка переходят новому ответственному
  (вторая ХО-сделка НЕ создаётся — существующая обновляется);
- KPI: прежнему пишется «Холодный звонок Не состоялся …», новому —
  «Запланирован» (план-запись на +1 с позже, чтобы хронология читалась);
- если ответственный тот же — пишется только новый «Запланирован»;
- **уже записанные элементы списков не редактируются никогда.**

### Режим C. «Взять в работу с созданием компании»

У лида компании нет, но работать нужно от компании.

```
createCompany=Y (+ любой stageMode)
```

Что делает: создаёт компанию с названием лида, привязывает к ней сделку,
ставит лиду «Установлена компания». Без флага сделка спокойно живёт **без
компании** — это штатный сценарий, фейковые компании не создаём.

> Компания из лида всегда важнее флага: если она у лида есть — берём её и
> новую не создаём, что бы ни стояло в `createCompany`.

## 2. Флаги

| Флаг | Значения | По умолчанию | Влияние |
|---|---|---|---|
| `stageMode` | `from_lead` \| `cold` \| `new` | `from_lead` | стадия создаваемой сделки ОП (`new` — «Новая», заявка стартует с начала воронки) |
| `isXo` | `Y` \| `N` | `N` | создавать ли ХО-сделку; при `Y` задачи закрываются, новая называется «Холодный обзвон …», пишется KPI |
| `createCompany` | `Y` \| `N` | `N` | создавать ли компанию, если её нет у лида |
| `taskMode` | `move` \| `close` | `move` | перенести открытые задачи или закрыть и поставить новую |
| `isRequest` | `Y` \| `N` | автодетект | legacy-признак «это заявка» от робота (site-метки + слово «Заявка»); заявку от входящего лида не отличает |
| `workKind` | `cold` \| `request` \| `lead` | автодетект по данным лида | ПЕРЕОПРЕДЕЛЕНИЕ вида холодной работы — СЛОВО в заголовке задачи и код события в KPI (см. §2.1) |
| `deadline` | `DD.MM.YYYY HH:mm:ss` | — | дедлайн новой задачи (локаль портала) |
| `name` | строка | название лида | название события в задаче |
| `responsible` | `user_123` / число | — | ответственный. НЕ передан: конвертация (`isXo=N`) оставляет ответственного ЛИДА, ХО (`isXo=Y`) распределяет round-robin по ОП (§7.2) |
| `department` | строка-намёк | — | из какого ОП выбирать round-robin (портал с несколькими ОП) |

`responsible` в вебхуке приходит как `user_123` (формат робота), в `/run` —
числом. См. предупреждение в DTO: тип query-поля обязан быть `string`.

Только в `/run` (кнопка фрейма, в query робота их нет): `excludeResponsible`
(кого round-robin не должен выбрать) и `transferredBy` (кто сам передал —
подсвеченная запись истории). Если включён `SALES_HOOK_WEBHOOK_AUTH_ENABLED`,
к query вебхука добавляется `&hookKey=<ключ из SALES_HOOK_WEBHOOK_KEYS>`.

### 2.1. Вид холодной работы и КОНТРАКТ ЗАГОЛОВКА

Вид определяется **автоматически по данным лида** — роботов править не нужно.
`workKind` в запросе остаётся только явным ПЕРЕОПРЕДЕЛЕНИЕМ.

Порядок решения — от СВОЕГО к ЧУЖОМУ: доверяем только тем полям, которыми
управляем сами (`LeadRequestDetectorService`).

1. `workKind` из запроса — если передан, спор окончен;
2. legacy-флаг `isRequest` (`Y` → `request`, `N` → `cold`);
3. **`op_lead_work_kind` — НАШЕ поле вида работы** (enumeration на лиде:
   Холодный / Заявка / Лид). Пишется этим же хуком при передаче лида в
   работу, дальше — источник истины: переживает ручные правки карточки и
   не зависит от настроек портала. Поля нет в слепке → идём дальше;
4. поля лидогена «Гарант» (`UF_CRM_REG_NUMBER`, `UF_CRM_LEAD_QUEST_URL`) —
   тоже наши, заполняются только у заявок → `request`;
5. наши метки пути заявки (`op_lead_site_status`/`op_lead_site_stage`) —
   говорят «работа входящая», вид не уточняют → по умолчанию `request`;
6. штатный `SOURCE_ID` — ПОСЛЕДНЯЯ подсказка и только чтобы уточнить вид
   поверх п.5 (`CALL`/`CALLBACK`/`EMAIL`/`IMOL`/`OPENLINE` → `lead`,
   `WEB`/`WEBFORM`/`RC_GENERATOR`/`STORE` → `request`). Объявить работу
   входящей он НЕ может: поле чужое, его правят руками и на многих порталах
   оно проставляется автоматически при ручном создании лида. Кастомные
   (числовые) коды сигналом не считаются. Решение по нему всегда попадает
   в лог и в `signals`;
7. ничего не сработало → `cold`.

Нераспознанный лид пишет в лог свой `SOURCE_ID` и список заполненных
UF-полей — по этой строке добирается настройка на новом портале.

Единственный канал до фрейма — **слово в заголовке задачи**: фрейм разбирает
TITLE (`parseTaskTitle`) и по нему шлёт в отчёт тип события.

| `workKind` | заголовок задачи | KPI `event_type` | тип события фрейма |
|---|---|---|---|
| `request` | `Холодный обзвон. Заявка. {N}` | `site` | `xoRequest` |
| `lead` | `Холодный обзвон. Лид. {N}` | `come_call` | `xoLead` |
| `cold` (или не передан) | `Холодный обзвон {N}` | `xo` | `xo` |

Формат самого заголовка менять нельзя — он же разбирается фронтом (см.
`LEAD_WORK_KIND_TITLE_WORD` в `shared/event-title/types/cold-work-kind.ts`,
там единственное место, где эти слова заданы).

Вид не сбрасывается после первого звонка: при планировании следующего шага
event-report наследует его от события, по которому отчитались, а ПЕРЕНОС
события правит только дедлайн — заголовок задачи остаётся прежним.

Заявка и входящий лид одинаково считаются «входящей работой»: у обоих
ставятся site-метки лида, таймер `op_lead_assigned_at` и SLA подтверждения —
различаются только слово в заголовке и код события в KPI.

## 3. Движение стадий: что двигается, а что нет

### 3.1 Стадия создаваемой СДЕЛКИ ОП

| Условие | Стадия сделки |
|---|---|
| `stageMode=cold` | `sales_cold` («Холодная») |
| `stageMode=from_lead`, у стадии лида есть зеркало | зеркальная стадия воронки (`lead_pres` → `sales_pres`) |
| `stageMode=from_lead`, зеркала нет | `sales_warm` («Переговоры») + warning |
| стадия не сопоставлена на портале | дефолтная стадия воронки + warning (не ошибка) |
| воронки ОП нет на портале | ❌ ошибка — работать негде |

### 3.2 Статус ЛИДА

| Ситуация | Что происходит со статусом лида |
|---|---|
| Лид сконвертирован штатно (CONVERTED) | **не трогаем** — Битрикс считает лид закрытым; пишем только поля и историю |
| `stageMode=from_lead` и стадия лида зеркальна стадии ОП | **остаётся на месте** — лид и сделка идут «параллельно» на одном этапе |
| У лида есть компания | → «Работа с компанией» (`lead_company_work`) |
| Компании нет | → «Взята в работу» (`lead_taken_in_work`) |
| Нужная стадия не установлена/не сопоставлена | статус не меняется + warning |

Дополнительно всегда проставляется `op_lead_status`: «Работа с компанией»
или «Работа со сделкой» — это наш собственный статус, он не зависит от
стадий Битрикса и работает даже без сопоставления стадий.

**Принцип:** любое подмножество сопоставленных стадий рабочее. Нет стадии —
шаг пропускается с warning, операция доходит до конца.

## 4. Какие связи записывает хук

Правило: лид ссылается на работу (`to_*`), а **каждая** связанная сделка —
основная И ХО — несёт обратные ссылки на лид. Так граф читается с любой
стороны в обеих ветках (и конвертация, и ХО).

| Где | Поле | Значение |
|---|---|---|
| Сделка ОП **и** ХО-сделка | `deal_from_lead_id` | `L_{leadId}` — лид-первоисточник (без конвертации Битрикса) |
| Сделка ОП **и** ХО-сделка | `deal_joined_leads` (multiple) | union со старым значением: все присоединённые лиды |
| Лид | `to_base_sales` | ссылка на основную сделку (`D_{id}`) — всегда, в обеих ветках |
| Лид | `to_xo_sales` | ссылка на ХО-сделку (при `isXo=Y`) |
| Лид | `op_lead_is_company` | 1, если компания есть/создана |
| Задача | `UF_CRM_TASK` | union: лид + сделка (+ компания, + ХО-сделка) |

Неустановленное поле пропускается молча — граф достроится, когда поле
поставят (см. `SALES_HOOKS_GUIDE.md`, раздел установки).

---

## 5. Идемпотентность

Перед записью хук читает состояние портала. Если у лида уже есть наша
сделка (`to_base_sales`), включается режим **reuse**: вторая сделка не
создаётся, связи доводятся, `deal_joined_leads` дополняется. Поэтому:

- повторный клик кнопки безопасен;
- робот, стрельнувший пять раз, даст одну операцию (окно тишины 1.5 с);
- «Преобразовать в работу» на фронте не показываем, если связка уже есть —
  это дубль по смыслу, даже если технически безопасен.

## 6. KPI и История — когда пишем, когда нет

Правило: **прошлое не переписываем, новое событие фиксируем.**

| Ветка | KPI / История |
|---|---|
| ХО (`isXo=Y`) | ✅ пишем «Холодный звонок Запланирован» — точно как классический ХО-хук |
| Перевод в работу (`isXo=N`) | ❌ не пишем: события «состоялось/запланировано» тут нет, работу отражает сделка |
| Любая ветка | ❌ существующие элементы KPI не редактируем и не удаляем |

### Как это устроено в коде (куда смотреть)

```
services/lead-to-work-kpi.service.ts        ← наш payload-билдер ХО-ветки
    queuePlanned(...)  → «Холодный звонок Запланирован …» (event_action=plan)
    queueNotHeld(...)  → «Холодный звонок Не состоялся …» (event_action=expired,
                          op_result_status=op_call_result_no) — при передаче
    работает БЕЗ компании: crm = [CO_?] + L_<lead> + D_<base> + [D_<xo>],
    код элемента — от companyId ?? leadId

shared/kpi-list-flow/services/kpi-list-flow.service.ts   ← универсальный писатель
    .flow(payload, entityId, buffer)
      → списки sales_kpi + sales_history (portal.getListByCode)
      → элементы кладутся в ТУ ЖЕ batch-группу → могут ссылаться на $result сделок

cold-hook/services/enities/kpi-list/cold-list.flow.service.ts  ← эталон-первоисточник
```

Вызов идёт из `LeadToWorkFlowService.queueKpi()` **внутри группы лида**,
до `endGroup()` — поэтому `$result[…]`-ссылки на создаваемые сделки
разрешаются. Списки не настроены на портале → `KpiListFlowService` пишет
warning и молча выходит (graceful, как всё остальное).

## 7. Фичи ХО-ветки

### 7.1 Определение «заявка или просто лид» (реализовано)

`services/lead-request-detector.service.ts`. Признаки заявки (любой
срабатывает):

- заполнено `op_lead_site_status` / `op_lead_site_stage` (наши поля заявки);
- заполнены поля лидогена портала (`UF_CRM_REG_NUMBER` — код партнёра,
  `UF_CRM_LEAD_QUEST_URL` — оценка).

Иначе — «просто лид». Влияет на:

- заголовок KPI-события: «Холодный звонок Запланирован. Заявка. {Название}»;
- название задачи: «Холодный обзвон. Заявка. {Название}»;
- первичное проставление `op_lead_site_status` («Взята в работу») и
  `op_lead_site_stage` («Запланирован звонок») — только ПУСТЫХ полей.

Если заявка не распознана, детектор пишет в debug-лог список заполненных
`UF_CRM_*` полей лида — так на новом портале можно добрать реальные имена
полей лидогена и дополнить `LEAD_REQUEST_UF_FIELD_NAMES`.

### 7.2 Round-robin выбор сотрудника (реализовано)

`services/lead-to-work-assignee.service.ts`. Когда `responsible` не
передан:

- **конвертация (`isXo=N`) круг не крутит вообще** — ответственный берётся
  с лида (`assigneeSource='lead'`); round-robin только в ХО-ветке, где
  распределение заявки и есть смысл операции. У лида нет ответственного →
  круг + предупреждение;
- кандидаты — активные сотрудники отдела продаж
  (`BxDepartmentStructureService`, mультирежим поддержан);
- параметр `department` — намёк, в каком именно подразделении выбирать
  (маппинг «код партнёра → отдел» держит Битрикс и присылает сюда id либо
  название). Сырая строка логируется как есть; матчатся по порядку: ОП →
  группа внутри ОП → **любой подотдел ОП** (`dep_{id}`, в том числе не
  названный «Группа …»). Подотдел найден, но пуст → берём его родительский
  ОП с warning; не смэтчилось вовсе — warning и выбор по всем ОП;
- выбор — **round-robin с курсором в app-cache** (`rr:{departmentKey}`,
  домен добавляет сам слой app-cache); курсор хранит userId, поэтому
  изменение состава отдела очередь не сбивает;
- в ветке конвертации при `reuse` ответственный **не переназначается**;
  в ХО-ветке повторный запуск — это передача (см. §1, режим B).

## 8. Что хук НЕ делает

- не редактирует и не удаляет существующие KPI/History (см. §6);
- не пишет KPI в ветке «перевод в работу»;
- не закрывает смежные сделки компании (в отличие от классического ХО);
- не двигает статус конвертированного лида;
- не создаёт компанию без явного флага;
- не трогает чужие воронки.

## 9. Карточка заявки и история обработки

- **Типизация** домена заявки — `@lib/portal-lib/pbx/pbx-lead-request`
  (enum'ы статусов/стадий/типов «не ЦА» с compile-time стражами против
  PBX_SALES_EVENT_FIELDS; никаких string-кодов).
- **Карточка**: `GET /lead-request/card/{leadId}?domain=…` — признак
  заявки, ссылка «Оценка» (открывать в соседней вкладке), код партнёра,
  статусы/стадии с вариантами, маркеры (дубли, чёрный список, НПП, boost),
  история обработки, готовность к продаже (missing-список).
- **Обновление**: `POST /lead-request/update` — типизированные коды;
  статус «Не ЦА» без типа отклоняется 400 (тип испрашивается фронтом).
- **История** (`op_lead_firstprepare_history`, multiple): append-only —
  ХО-ветка хука пишет «ХО назначен/передан», финалы «Звонков» — «Продажа/
  Отказ», ручные правки карточки — сводку изменений; прошлые записи не
  редактируются никогда.
- **Синк финалов**: event-report при продаже/отказе двигает статусы всех
  связанных лидов (LEAD_ID ∪ deal_from_lead_id ∪ deal_joined_leads) +
  `dto.leadSync.notCaTypeCode` с фронта.
- **stageMode='new'**: базовая сделка создаётся в «Новая» (не «Холодная») —
  для заявок, стартующих с начала воронки.
- **Лид в задачах**: task-flow event-report наследует `L_*` из текущей
  задачи и полей сделки — из лида всегда видно, что происходит.

## 10. Смежный хук: проверка на дубли из сущности

`sales-hooks/duplicate-check` — принимает тип+id сущности (lead / company /
deal / contact), проводит глубокую проверку дублей (реквизиты, ИНН,
подстрока названия — уровень DEEP по умолчанию) и пишет итог комментарием
в **timeline этой сущности**: заголовок, нумерованные кандидаты с
признаками совпадения («ИНН 4826… (реквизиты)») и ссылками на карточки,
сводка сигналов. Для лида дополнительно проставляются маркеры
`op_lead_is_duplicate_check` / `op_lead_is_duplicate` (graceful).
