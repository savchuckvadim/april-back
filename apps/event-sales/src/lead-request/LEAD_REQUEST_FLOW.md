# Путь заявки: полная документация (ХО → принятие → финал)

## Для клиента (без технических деталей)

Каждая заявка с сайта проходит контролируемый путь:

1. **Появилась** — заявка создана, видна руководителю в воронке лидов.
2. **Назначена менеджеру** — система сама выбирает сотрудника отдела
   по очереди (нагрузка распределяется равномерно) и ставит ему работу:
   сделку в его воронке и задачу «Холодный обзвон».
3. **Принята в работу** — менеджер подтверждает принятие кнопкой в
   приложении «Звонки» (или просто двигает свою сделку). Пока не
   подтвердил — отправка отчётов заблокирована. Система замеряет время
   от назначения до принятия.
4. **Не принял за N минут** (порог настраивается) — заявка автоматически
   передаётся следующему сотруднику отдела, руководитель получает
   уведомление. Менеджер может и сам передать заявку — это фиксируется.
5. **Работа** — звонки, презентации: всё это события отчётов, они
   двигают статусы заявки и пишутся в её историю.
6. **Финал квалификации — обнаружена компания.** С этого момента ясен
   исход заявки: присоединена к существующей работе, стала началом
   продажи, дошла до презентации, оказалась не целевой или отказ.
   Дальше жизнь продолжается в компании и сделках.

Каждый шаг записывается в **историю обработки заявки** — руководитель
видит всю хронологию: кто получил, кто не взял, кому передали, когда
приняли, чем закончилось. Прошлые записи никогда не переписываются.

Если у заявки найдены **возможные дубли** — она помечается, менеджер
обязан разобрать их до фиксации продажи (продажа заблокирована).

## Для разработчика и внедрения

### Аксиома
Жизненный цикл заявки заканчивается В МОМЕНТ ОБНАРУЖЕНИЯ КОМПАНИИ.
Стадии = необратимый путь (финалы Продажа/Отказ — стадии), статус =
свёртка истории (состояние внутри бизнес-процесса), причины — отдельные
поля. Назначение ≠ принятие: разница между ними = время первичной
обработки (`op_lead_firstprepare_long`).

### Карта стадий лида (наши, install через pbx-install)
```
Появилась → Назначена менеджеру (lead_assigned) → Взята в работу
(lead_taken_in_work) → … → Работа с компанией (lead_company_work) → финалы
```
`lead_assigned` — МАРКЕР «ждёт принятия»: по нему работает SLA-cron и по
выходу из него понятно, что заявка принята.

### Все хуки семейства sales-hooks (`apps/event-sales/src/sales-hooks/`)

| Хук | Маршруты | Назначение | Кто зовёт |
|---|---|---|---|
| **lead-to-work** | `POST /sales-hooks/lead-to-work/webhook` (silence), `POST …/run` (очередь+operationId) | Лид → работа ОП: компания (по флагу), базовая сделка, ХО-сделка (isXo=Y), задача, стадии лида, связи, KPI, история. Повторный вызов = передача | Робот на новый лид; кнопка фрейма; кнопка «Передать другому»; SLA-cron |
| **lead-accept** | `POST /lead-request/accept/webhook` (silence, ПАЧЕЧНЫЙ) | Принятие заявки менеджером (см. раздел «Принятие») | Робот на смену стадии СДЕЛКИ (шлёт dealId) или стадии лида (leadId) |
| **duplicate-check** | `POST /sales-hooks/duplicate-check/webhook`, `…/run` | Глубокая проверка дублей (lead/company/deal/contact), итог в timeline + маркеры `op_lead_is_duplicate*` | Робот; кнопка фрейма |
| **convert-normalizer** | `POST /sales-hooks/convert-normalizer/webhook`, `…/run` | Ручная конвертация мимо хука → self-healing связей (deal_from_lead_id, deal_joined_leads, to_base_sales) | Робот onCrmDealAdd |
| **merge-duplicates** | `POST /sales-hooks/merge-duplicates/run` | Слияние дублей: dryRun-план (default) → выполнение с planHash | Кнопка руководителя |
| **transfer-work** | `POST /sales-hooks/transfer-work/give`, `…/take` | Передать/забрать ВСЮ работу по компании (сделки, задачи) | Кнопки фрейма |
| **reject-buffer** | `POST /sales-hooks/reject-buffer/webhook`, `…/run` | Буфер отказников: сделки → fail-стадии, задачи закрыть | Робот; кнопка |

Общая механика: вебхук → silence-дебаунс (бурст по сущности схлопывается,
окно 1.5 с) → очередь `EVENT_SALES_HOOK_OPS` → use-case с ОБЯЗАТЕЛЬНОЙ
пачечной предобработкой (batch-чтение всей пачки до расчёта, batch-запись
после). Кнопка → `/run` без silence, статус — `GET
/sales-hooks/operations/{operationId}` + WS `sales-hook:done|error`.

### ХО из лида (lead-to-work) — детально

Параметры вебхука (query) / run (body):

| Параметр | Значения | Смысл |
|---|---|---|
| `leadId` | число | обязателен |
| `responsible` | id | явный ответственный; не передан → round-robin |
| `department` | id ИЛИ название | намёк, из какого ОП выбирать (формат робота логируется `[assignee]`) |
| `createCompany` | Y/N (N) | создать компанию, если нет |
| `stageMode` | from_lead / cold / **new** | стадия базовой сделки; для заявок — `new` |
| `taskMode` | move / close | move — перенос задач с префиксом «Звонок»; close — закрыть и создать новую |
| `isXo` | Y/N | Y = классический ХО: +ХО-сделка, задача «Холодный обзвон», **KPI пишется** |
| `isRequest` | Y/N | Явный признак «это заявка» от робота (главнее автодетекта по полям); не передан — автодетект |
| `deadline`, `name` | строка | дедлайн задачи / название события |
| `excludeResponsible`, `transferredBy` | id (только run) | передача: исключить прежнего из round-robin; «сам передал» — подсветка в истории |

**Инвариант «одна открытая пара»** (как в классическом ХО): при каждом
прогоне хук собирает все сделки лида (обратные ссылки `to_base_sales`/
`to_xo_sales` + свои по `deal_from_lead_id` + конвертационные по `LEAD_ID`),
берёт в работу ПОСЛЕДНЮЮ открытую основную и последнюю открытую ХО, а
остальные ОТКРЫТЫЕ закрывает в fail-стадию своей воронки. Закрытые сделки
не трогаются никогда. Поэтому повторный запуск (в том числе «поправили
руками и передали заново», до или после подтверждения) не плодит пары.

Что делает при `isXo=Y, stageMode=new` (режим «ХО из заявки»):
- лид → стадия «Назначена менеджеру» (`lead_assigned`), site-метки
  «Появилась»/«Назначена» (только пустые), `ASSIGNED_BY_ID` = выбранный;
- базовая сделка в «Новая» + ХО-сделка; на ОБЕИХ — `deal_from_lead_id`,
  `deal_joined_leads`; в лиде — `to_base_sales`, `to_xo_sales`;
- задача «Холодный обзвон[. Заявка. {Название}]» на выбранного;
- KPI «Холодный звонок Запланирован[. Заявка. {Название}]» (+1 с);
- история: «ХО назначен: {id}» / «передан → {id}» / «⚠ сам передал».

**Повторный вызов по тому же лиду = передача**: вторая ХО-сделка НЕ
создаётся — существующая передаётся новому; задачи прежнего закрываются,
ставится новая; KPI-пара «Не состоялся» прежнему + «Запланирован» новому
(старые элементы списков НИКОГДА не редактируются).

**Round-robin**: кандидаты — активные сотрудники ОП (по department-намёку,
иначе все ОП; при передаче — отдел передающего), курсор в app-cache,
`excludeResponsible` исключается, если он не единственный.

### Принятие — детально

**Признак «подтверждение нужно» роботу знать НЕ требуется.** Ручка
идемпотентна: бэк сам определяет необходимость по истории
`op_lead_firstprepare_history` (append-only, источник истины) — принятие
валидно только ПОСЛЕ последней записи назначения («ХО назначен/передан»).
Уже принята → `already=true`, ноль записей. Робот может стрелять на
каждую смену стадии — silence + идемпотентность гасят всё лишнее.
Резервный признак (истории нет) — стадия лида `lead_assigned`.

**Кто фиксируется принявшим** — отдельное поле НЕ нужно, «на кого надо
сделать что принял» уже хранится в `ASSIGNED_BY_ID` лида (хук ставит его
при назначении и КАЖДОЙ передаче):
- кнопка UI шлёт `userId` явно;
- вебхук робота `userId` не шлёт → бэк берёт ответственного лида.

Что происходит при принятии (всё graceful — нет поля/стадии → warning):
- лид → стадия «Взята в работу» (`lead_taken_in_work`);
- site_status/site_stage → «Взята в работу»;
- `op_lead_firstprepare_long` = секунды от ПОСЛЕДНЕГО назначения до
  принятия (пишется только если пусто — передачи не перетирают);
- история += «Заявка принята в работу: {id}»;
- базовая сделка → «Холодная» (`sales_cold`) — «окончательно в ХО».

Ручки:
- `POST /lead-request/accept` `{domain, leadId|dealId, userId?}` —
  прямая (кнопка UI, мгновенный ответ);
- `POST /lead-request/accept/webhook?leadId=…|dealId=…` — через
  silence-буфер + пачечный хук (2 batch-чтения + batch-запись на пачку
  любого размера); тело — стандартный вебхук Битрикса (домен из auth).

**Настройка робота на подтверждение** (менеджер живёт в воронке сделок):
1. Робот в воронке ОП на смену стадии сделки **из «Новая» в любую** →
   исходящий вебхук `POST {backend}/api/lead-request/accept/webhook?dealId={{ID}}`.
2. Условие робота (рекомендация, не обязательно): `deal_from_lead_id`
   заполнен — чтобы не дёргать ручку по сделкам не из заявок. Без
   условия тоже безопасно (бэк отсеет: лид не найдётся или already).
3. Опционально второй робот на стадию ЛИДА «Взята в работу» (двинул
   руководитель) → тот же вебхук с `?leadId={{ID}}`.

Эхо-защита (принятие двигает сделку → робот стрельнёт ещё раз):
ручка идемпотентна (no-op), SLA-cron принятых не видит, dispatch дедупит
fingerprint.

**SLA непринятия**: cron раз в 10 мин (включение и порог — админка →
портал → Settings → event-sales: `lead_intake_sla_enabled`,
`lead_intake_sla_minutes`, `lead_intake_sla_max_per_run`). Выборка одним
индексным запросом: `STATUS_ID=lead_assigned + <DATE_MODIFY`. Сделка уже
двинута из «Новая» → self-healing принятие задним числом (страховка от
потерянных вебхуков — Битрикс не ретраит). Иначе: история «Не принял за
N мин» → передача повторным ХО (excludeResponsible, отдел прежнего) →
`im.notify` руководителю ОП (UF_HEAD) со ссылкой на лид.

### Фронт «Звонки» — что ожидается

Фича `modules/features/LeadRequestCard` (все данные — с
`GET /lead-request/card/{leadId}`, перечитывается при КАЖДОМ
монтировании панели — состояние принятия всегда свежее):

| Элемент | Поведение |
|---|---|
| **LeadRequestAcceptBar** | 3 состояния по `isAccepted` + `assignedById` vs текущий пользователь: принята → скрыт; не принята, назначена МНЕ → янтарный блок «Принять в работу» / «Передать другому»; не принята, назначена ДРУГОМУ → серый инфоблок без кнопок («принимает новый ответственный») |
| Блокировка отправки | `useLeadRequestSendBlock`: непринятая своя → «Сначала примите заявку в работу»; чужая → «Заявка назначена другому сотруднику». Кнопка «Отправить» в ItemActions задизейблена с подписью |
| «Принять в работу» | `POST /lead-request/accept` (+userId текущего) → перечитка карточки |
| «Передать другому» | `POST /sales-hooks/lead-to-work/run` `{isXo:Y, stageMode:new, taskMode:close, transferredBy, excludeResponsible}` → перечитка с задержкой 2.5 с (операция в очереди) |
| Карточка | заголовок «Заявка/Лид», ссылка «Оценка» (соседняя вкладка), код партнёра, статусы/стадии/не-ЦА (селекты с портальными названиями), булевы маркеры, история (newest-first), readiness-бейдж «Для продажи не отмечено: …» |
| Финал «отказ» | в блоке отказа отчёта — селект «Тип не ЦА» → `leadSync` payload (бэк валидирует «Не ЦА без типа → 400») |
| Настройки | `GET /app-settings/event-sales?domain=…` при старте, серверные флаги ложатся поверх legacy domain-config |

Точки встройки: EntityBoard (лид = первый открытый связанный) и
EventItem (лид задачи) — панель lazy.

### История заявки (`op_lead_firstprepare_history`)
Append-only строки «DD.MM.YYYY HH:mm — текст», cap 100, дедуп двойного
клика. Пишут: назначение/передача (lead-to-work), принятие (accept),
SLA («Не принял за N мин»), правки карточки, синк финалов. По ней
считаются: `isAccepted`, `firstprepare_long`.

### Слепок портала: почему «поля установлены, а в лиде пусто»

Слепок портала (поля, стадии, воронки) кэшируется в Redis ключом
`portal_{domain}` на **10 часов**. Поля, установленные после кэширования,
до истечения TTL считаются «неустановленными» — хук молча их пропускает
(graceful degradation), и записи теряются без единой ошибки.

Что сделано, чтобы это не повторялось:
- **установщик сбрасывает кэш сам** — `syncWithDb` всех CRM-сущностей,
  typed-полей и списков принимает домен и инвалидирует слепок;
- **хуки лечатся сами** — runner перед выполнением проверяет
  `portal.hasEntityFields('lead')`; пустая секция = слепок протух, портал
  перечитывается принудительно (у сброса кулдаун 5 мин на домен);
- **ручной сброс** — `POST /api/pbx-portal-cache/invalidate?domain=…`
  (pbx-install) для изменений мимо установщика;
- **диагностика** — если в `lead.update` не попало ни одного UF-поля, в лог
  идёт `[lead-fields] Портал не отдаёт ни одного UF-поля ЛИДА …`;
- **ошибки батча видны** — runner логирует `result_error` по каждой
  команде (`команда lw_lead_42 не выполнена — …`): раньше неудачная
  команда молча терялась, а симптом выглядел как «поле не заполнилось».

### Формат значений crm-полей

Правило Битрикса: поле с ОДНИМ разрешённым типом сущности (SETTINGS)
хранит голый id (`1024`), с НЕСКОЛЬКИМИ — id с префиксом (`D_1024`).
Неверный формат не даёт ошибки — значение просто не сохраняется. Поэтому
формат берётся из ФАКТИЧЕСКИХ привязок поля портала
(`LeadUfDefinitionsService`, кэш 10 мин), а не из нашей константы.

### Идемпотентность и защита от шторма
- вебхуки — через silence-дебаунс; принятие валидно только после
  ПОСЛЕДНЕГО назначения (после передачи — принимать заново);
- эхо робота гасится: ручка no-op, cron не видит принятых, fingerprint;
- cron: Redis-лок, cap на проход, ошибка домена не роняет цикл;
- у каждого хука пачечная предобработка (хук = ×100–200 вызовов).

### Правило списков
KPI/History никогда не редактируются. Передача пишет ПАРУ:
«Не состоялся» прежнему (SLA-сигнал руководителю) + «Запланирован»
новому (+1 с). Переписывание задним числом запрещено осознанно.

### Чек-лист внедрения на портале
1. Установить стадии лида (pbx-install, кнопка «Установить недостающие»):
   `lead_assigned`, `lead_taken_in_work`, `lead_company_work`.
2. Переустановить crm-поля кнопкой (SETTINGS-фикс — иначе `to_base_sales`
   молча не сохраняется).
3. Робот на НОВЫЙ лид (или нужную стадию) → `POST
   {backend}/api/sales-hooks/lead-to-work/webhook?leadId={{ID}}&isXo=Y&stageMode=new&taskMode=close[&department=…]`.
4. Робот на смену стадии сделки из «Новая» → `POST
   {backend}/api/lead-request/accept/webhook?dealId={{ID}}`.
5. Админка → портал → Settings → event-sales: включить SLA, задать порог.
6. Прогнать один лид, посмотреть лог `[assignee]` (формат
   department-намёка) и историю заявки.
