# Смарт «AI-анализ звонков»: кто и когда заполняет каждое поле

Справочник для разбора вопросов «почему поле пустое». Актуален на 05.08.2026.

## Три писателя элемента (по порядку во времени)

| # | Писатель | Когда срабатывает | Что делает |
|---|----------|-------------------|-----------|
| 1 | **Каркас** — `CallReportBaseItemService` | Сразу после транскрибации+классификации+GigaChat (флаг «Элемент смарт-процесса» в настройках AI портала) | Создаёт элемент: связи, идентификация звонка, тип, транскрипт, GigaChat-резюме/рекомендации. Привязывает родную запись звонка (плеер) в таймлайн |
| 2 | **Глубокий разбор** — `AgentAnalysisIntakeService` (фокус-разбор, fallback цельный) | Через минуты после каркаса (если «Глубокий разбор» включён и звонок не отсеян гейтом нерелевантности) | Дополняет ТОТ ЖЕ элемент (upsert по `xmlId=aicall_{activityId}`): все оценки, разделы, рекомендации, флаги. Пишет разделы и диалог в таймлайн элемента |
| 3 | **Ночной ревизор** — `CallRevisionService` | 23:30 МСК, если включён тумблер «Ночной ревизор» | Обновляет ПОСЛЕДНИЙ элемент сущности: «Рекомендации по сделке» (+невыполненные обещания), риски, приоритет разбора; коммент «Ночная ревизия» в таймлайн сделки |

**Главные причины пустых полей разбора (весь блок сразу):**
1. Глубокий разбор не записался — `crm.item.update` падал у Битрикса с
   «Row size too large (>8126)»: строка таблицы смарта вмещает лишь ~9-10
   ДЛИННЫХ (>768 байт) текстовых полей, причём обрезка длинного текста не
   помогает — платится фиксированный 768-байтовый префикс (подробно — скилл
   `.claude/skills/bitrix-field-limits`). С 10.08.2026 запись бюджетная:
   все поля → без транскрипта → только приоритетные тексты <700 байт →
   минимум; **всё выброшенное уходит полным текстом в таймлайн элемента**
   (порядок: резюме GigaChat → рекомендации → остальное, частями по 8к).
   Полный отказ алертится в Telegram.
2. Разбор выключен («Глубокий разбор» = Выключено) или звонок отсечён гейтом
   нерелевантности — тогда это ожидаемо.
3. Элемент создан, а разбор упал по LLM-ошибке — дольётся повторным прогоном
   (`POST /call-report/analyze` по этому activityId).

## Поля по группам

Обозначения писателей: **К** — каркас, **Р** — глубокий разбор, **Н** — ночной
ревизор, **код** — вычисляется кодом, не моделью.

### Связи и идентификация (пишет К, всегда)

| Поле | Источник | Пусто когда |
|------|----------|-------------|
| Название элемента | код: «Исходящий звонок от … · N мин» | никогда |
| Сделка/Лид (parentId) | строка транскрибации (владелец звонка) | звонок без CRM-владельца — **в разбор такие не попадают вовсе**: сканер отсеивает всё, кроме OWNER_TYPE_ID сделки/лида (`skippedNonDeal`). Поэтому у любого элемента в input ЕСТЬ либо dealId, либо leadId. Звонок по лиду даёт связь «Лид» (parentId1), а поле «Сделка» остаётся пустым законно |
| Компания, Контакт, Ответственный | crm.deal.get / crm.lead.get | нет в CRM-карточке владельца звонка (частый случай: сделка/лид без компании) |
| ID активности, ID звонка, Дата звонка, Длительность, Менеджер, ID транскрибации | телефония/строка БД | практически никогда |
| Основная сделка (DEAL_MAIN) | К: владелец-сделка; Р может уточнить | звонок по лиду без сделки |
| Сделка-презентация, Сделка ХО | **Р** (relatedDeals) | разбор не связал |

### Классификация (К + Р)

| Поле | Источник | Пусто когда |
|------|----------|-------------|
| Тип звонка (CALL_TYPE) | **К** ← дешёвый классификатор | классификация выключена/упала; значения нет в справочнике (после добавления типа — переустановить смарт) |
| Звонок результативный, С кем говорили, Тон клиента | **Р** | разбора не было |
| Специальность собеседника (SPECIALIST: бухгалтер/юрист/кадровик/руководитель/другой) | **Р** — по лексике разговора; должность из CRM (POST лида/контакта) приходит подсказкой в паспорте | явных признаков в разговоре нет (модель обязана вернуть null, а не гадать); разбора не было |
| Хвост: разбор AI / 5К: разбор AI (кратко, <700 байт; полные тексты — в таймлайне) | **Р** — только презентация/решение | тип звонка другой; разбора не было |
| Хвост: отчёт менеджера / 5К: отчёт менеджера | **Сверка** (утренний крон) — «ОП Хвост»/«ОП Пять К» сделки-презентации + с 26.08.2026 гранулярный чеклист: op_xvost_* из сделки и 9 ответов op_5k_* из ЛИДА (по LEAD_ID сделки) | сверка выключена; менеджер не отчитался; сделка не связана с разбором |
| Гранулярный чеклист AI — 14 boolean: «Хвост AI: КП предложено / наполнение озвучено / цена озвучена / дата решения назначена / дата согласована» + «5К AI: клиент что хочет / готов / цена; компания кто / как / подбор верен; коллеги; конкурент; критерии выбора СПС» | **Р** (с 26.08.2026) — те же вопросы, что менеджер заполняет в сделке (op_xvost_*) и лиде (op_5k_*); итоги HVOST_DONE/FIVE_K_DONE пересчитываются КОДОМ: пройдено = все пункты «да». null-пункт («не тот тип звонка») поле не пишет | тип звонка не презентация/решение; разбор до 26.08; смарт не переустановлен (поля не созданы) |

### Транскрипт и первичный RAG (К)

| Поле | Источник | Пусто когда |
|------|----------|-------------|
| Транскрипт, часть 1-4 | **К** (сырой текст); **Р** заменяет диалогом по ролям | текст короткий — заполнена только часть 1; **первый кандидат на выброс при деградации row size**. С 16.08.2026 текст при выбросе ГАРАНТИРОВАННО постится в таймлайн элемента целиком: «📜 Транскрипт звонка — часть N из M» (кусками по 8к, часть 1 сверху); если разбор прислал диалог по ролям — в таймлайне вместо этого диалог от intake (без дублей) |
| Резюме GigaChat (RAG), Рекомендации GigaChat | **К** ← GigaChat | GigaChat упал (TLS/ключ) |

### Итоги разбора (все — Р; пустые = разбор не записался)

| Поле | Примечание |
|------|-----------|
| Резюме звонка (SUMMARY) | ТОЛЬКО разбор. Раньше каркас клал сюда копию GigaChat — убрано 05.08.2026 (в карточке было два одинаковых резюме) |
| Оценка звонка (1-10), Объяснение оценки | |
| Взвешенная оценка 0-100 | **код**: Σ score×relevance / Σ relevance × 10 по разделам с relevance>0 (если модель не прислала свою) |
| Соответствие скрипту, % | модель; нужна методичка со скриптом в базе знаний, иначе оценка приблизительная |
| Анализ речи менеджера (спич) | фокус ФОРМА (speechAnalysis) |
| Доля речи менеджера %, Вопросов задано | Внутренний конвейер: **оценка LLM** (фокус ФОРМА, с 26.08.2026 — до этого поля ПУСТОВАЛИ: точный подсчёт кодом требует диалога по ролям, который умеет присылать только внешний агент-контур). Внешний агент: **код** пересчитывает по размеченному диалогу и перекрывает LLM. Точность станет кодовой после стерео-диаризации |
| Рекомендации сотруднику (тренировать) | |
| Рекомендации по сделке (RECOMMENDATIONS) | Р; **Н** дописывает свод + невыполненные обещания |
| Приоритет разбора (coaching) | Р; **Н** может повысить |
| Имя агента-аналитика | **код**: call-report-analyzer |
| Версия скилла агента | **код**: internal-focus-v2 (до 05.08.2026 не заполнялась — доделано) |

### Содержание продажи (Р)

| Поле | Пусто когда |
|------|-------------|
| Потребности выявлены + Потребности | тема не звучала → false/пусто (правило фактов: модель НЕ выдумывает) |
| Презентация проведена + Предложенные продукты | продукты не назывались → пусто |
| Возражения клиента / Отработка возражений | возражений не звучало → пусто. Это НОРМА, не ошибка |
| Цена обсуждалась, Конкурент упомянут + Конкуренты, Категории возражений, Риск-флаги, Категория отказа | закрытые справочники; тема не звучала → false/пусто |
| Следующий шаг (флаг/текст/дата) | шаг не назначен → false |

### Разделы разбора: 7 × (актуальность, оценка, разбор, рекомендации) — Р

- `relevance=0` — этап физически не мог состояться (недозвон, автоответчик):
  оценка/разбор не заполняются, **это норма**.
- Этап был возможен, но провален — высокий relevance + низкая оценка.
- Все 28 полей пустые разом → разбор не записался (см. причины выше).

### Привязки отчётности (Р, опционально)

KPI_ITEM_*/HISTORY_ITEM_*/RELATED_REPORTS — только если разбор сопоставил
звонок с записями списков отчётности; для внутреннего аналитика пока
заполняются редко (полноценно — Фаза 4, KPI-сверка).

## Диагностика за 2 минуты

1. Пустые ВСЕ поля разбора → лог за время звонка: «Строка смарта не влезла…»
   (теперь чинится само) или «Глубокий разбор не выполнен…»; повторный прогон:
   `POST /call-report/analyze {domain, activityId}`.
2. Пустой только транскрипт → сработала деградация row size (текст в таймлайне
   элемента и в БД `transcriptions`).
3. Пустой CALL_TYPE → классификатор выключен/упал, либо в справочнике нет
   значения (переустановить смарт после добавления типов).
4. Пустые «Возражения»/«Цена»/«Конкуренты» при заполненном остальном →
   тема в разговоре не звучала; поле честно пустое.
5. **Пустые связи (сделка/компания) у всех элементов** — с 26.08.2026 система
   отвечает сама: writer сверяет отправленные связи с эхом созданного элемента
   и пишет либо `связи НЕ отправлялись` (warn — у звонка нет владельца/клиента,
   привязывать нечего), либо `Битрикс НЕ СОХРАНИЛ связи [...]` (error +
   Telegram — портал отбросил поле). До этого дропа не было видно вообще:
   Bitrix отвечает 200 и молча отбрасывает поля, которых у типа нет.
   Три причины дропа: у типа нет `relations.parent` (нет parentId2/parentId1),
   `isClientEnabled='N'` (нет companyId/contactId), crm-поле DEAL_MAIN без
   `settings.DEAL` — так создавались поля ДО 22.07.2026, и переустановка их
   не чинила (существующие поля пропускались). Теперь установщик доводит
   привязку существующих crm-полей (`repairCrmFieldSettings`) — достаточно
   повторного `POST /call-report/install-smart`; уже созданные элементы
   значений не получат, их доливает повторный `POST /call-report/analyze`.
   Ручная проверка портала: `userfieldconfig.list` по `CRM_{typeId}` →
   у `UF_CRM_{typeId}_DEAL_MAIN` смотреть `SETTINGS.DEAL='Y'`;
   `crm.item.list` (entityTypeId смарта, select `id,parentId2,parentId1,
   companyId,ufCrm{typeId}DealMain`) — видно, что реально сохранилось.

6. **Пустой «разбор» при заполненных оценке/рекомендациях** (жалоба
   27.08.2026) — строка карточки не вмещала все тексты, и длинные разборы
   выбрасывались целиком. С 27.08.2026 действует БЮДЖЕТНОЕ УЖАТИЕ: тексты
   не выбрасываются, а ужимаются под общий бюджет строки (~6.5к байт на
   все поля разом, поровну), полные версии — в таймлайне и в недельном
   Excel. Несколько запросов подряд эту физику не обходят: лимит — на
   ширину СТРОКИ таблицы, а не на размер запроса.
7. **«Array» или «[object Object]» в текстовом поле** — в поле уехала
   структура вместо строки, PHP-Битрикс сохранил её как литерал «Array».
   Writer теперь приводит такие значения к тексту сам и пишет warn с
   именем поля (`coerceScalar`).
8. **Куски LaTeX в текстах** (`$\leftarrow$`, `\textbf{…}`, `100\%`) —
   артефакт LLM; чистится на входе (`text-sanitize.util.ts`).
9. **Название элемента вдруг стало «AI-анализ звонков: звонок #N»** —
   дописывающий проход (ночной ревизор, сверка презентаций) не знает
   паспорта звонка и раньше перезаписывал заголовок техническим. С
   27.08.2026 название пишется только при создании элемента.

## Недельный Excel-отчёт

Всё, что физически не помещается в карточку, собирается в книгу Excel:
листы «Звонки» (паспорт + ПОЛНЫЕ разборы, речь, хвост/5К, сверка,
транскрипт), «Разделы разговора» (полный разбор каждого этапа) и
«Сводка». Крон — пятница 19:00 МСК по порталам с `weeklyReportEnabled`;
файл кладётся на Диск (`weeklyReportFolderId` — папка рабочей группы,
иначе хранилище приложения), получателям из `weeklyReportRecipients`
(bitrix-id через запятую в админке) уходит уведомление со ссылкой.
Ручной запуск: `POST /call-report/weekly-report {domain, days}`.
Лимит ячейки Excel — 32767 символов, длинные транскрипты режутся с
явной пометкой.
