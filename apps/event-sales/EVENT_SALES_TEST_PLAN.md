# Event Sales — план ручного тестирования (хуки, дубли, встройки)

Что и в каком порядке прогонять после установки полей и деплоя. Сценарии
идут по возрастанию риска: сначала read-only (ничего не портит), потом
записывающие, в самом конце — разрушающий merge.

**Полигон:** `garantservisvoronezh.bitrix24.ru` (поля установлены 08.08.2026).
Заведите 2–3 тестовых лида и 1 тестовую компанию, чтобы не трогать боевые.

Легенда результатов:
- ✅ — так и должно быть;
- ⚠️ — ожидаемое предупреждение (`warnings` в ответе), НЕ ошибка: значит
  на портале что-то не сопоставлено, шаг пропущен осознанно;
- ❌ — баг, пишем в задачу с `operationId` и телом ответа.

## 2. Лид → работа (главный записывающий хук)

Порядок важен: каждый следующий пункт опирается на состояние из предыдущего.

### 2.1 Лид БЕЗ компании, простой запуск
```
POST /api/sales-hooks/lead-to-work/run
{ "domain": "...", "leadId": <лид без компании>, "responsible": <userId> }
```
Затем `GET /api/sales-hooks/operations/{operationId}?domain=...` до `status: done`.

Что смотреть:
| Где | Ожидание |
|---|---|
| ответ операции | `result.items[0].baseDealId` — id созданной сделки; `reused: false` |
| Битрикс, сделка | создана в воронке ОП; **название = название лида** (компании нет) |
| поля сделки | «Лид из которого создана» = наш лид; «Лиды присоединённые» содержит его же |
| Битрикс, лид | поле «to_base_sales» указывает на сделку; статус сдвинут (или ⚠️ если стадия не сопоставлена) |
| задача | создана «Звонок …», в группе ОП, привязана к лиду и сделке |
| KPI-список | ✅ НИЧЕГО не добавилось — хук не пишет KPI |

### 2.2 Повторный запуск того же лида (идемпотентность)
Тот же запрос ещё раз.
- ✅ `reused: true`, `baseDealId` тот же, **вторая сделка не создана**;
- ✅ в «Лиды присоединённые» лид не задвоился.

### 2.3 Лид С компанией
- ✅ компания из лида взята за основу (`companyId` в ответе, сделка привязана к ней);
- ✅ `company.set` не вызывался — новая компания не создана;
- ✅ у лида проставлен «Установлена компания», статус → «Работа с компанией».

### 2.4 Создание компании по флагу
`"createCompany": "Y"` на лиде без компании.
- ✅ компания создана с названием лида, сделка привязана к ней (в ответе `companyId`).

### 2.5 Ветка ХО
`"isXo": "Y"`.
- ✅ создаются ДВЕ сделки: ОП + ХО (`xoDealId`);
- ✅ открытые задачи закрыты, новая называется «Холодный обзвон …»;
- ✅ смежные сделки компании НЕ закрыты (в отличие от старого ХО-хука).

### 2.6 Задачи: move vs close
Лид с 2–3 открытыми задачами.
- `"taskMode": "move"` → ✅ задачи получили префикс «Звонок», нового ответственного, группу ОП; повторный запуск НЕ даёт «Звонок Звонок …»;
- `"taskMode": "close"` → ✅ старые завершены, создана одна новая.

### 2.7 Робот (silence-путь)
```
POST /api/sales-hooks/lead-to-work/webhook?leadId=..&responsible=user_..
тело: обычный вебхук Битрикс (auth.domain)
```
- ✅ мгновенный ответ `accepted: true`;
- ✅ через ~2 с в Битриксе появляется результат (окно тишины);
- ✅ если робот стрельнул 5 раз подряд по одному лиду — операция ОДНА (в логах «отброшена как повтор» — это ✅).

## 3. Нормализатор ручной конвертации

### 3.1 Штатная конвертация мимо хука
В Битриксе руками сконвертировать тестовый лид (создастся сделка).
Если робот `onCrmDealAdd` уже висит — ничего не делаем, иначе:
```
POST /api/sales-hooks/convert-normalizer/run { "domain": "...", "dealId": <новая сделка> }
```
- ✅ `healed: true`, у сделки заполнились «Лид из которого создана» и «Лиды присоединённые»;
- ✅ у лида появилась ссылка на сделку (если поле было пустым);
- ✅ повтор — `healed: false` (уже нормализовано), ничего не переписывается.

### 3.2 Конвертация лида, у которого УЖЕ есть наша работа
Лид из сценария 2.1 (у него есть наша сделка) сконвертировать руками.
- ✅ в `warnings` — «у лида уже есть наша сделка … кандидат на merge»;
- ✅ ничего не сломано: обе сделки живы, решение о merge за человеком.

### 3.3 Обычная сделка (не из конвертации)
Запустить нормализатор на сделке без `LEAD_ID`.
- ✅ `healed: false`, ни одной записи в Битрикс.

### 4.2 Забрать (`/take`) — то же тело
- ✅ поведение идентично (разные маршруты под будущие права).

- ✅ `groups[0].survivorId` = САМАЯ СТАРАЯ компания, `victimIds` — остальные;
- ✅ в ответе `planHash`;
- ✅ сделки чужих воронок — в `skipped` с причиной.

### 6.2 Выполнение

### 6.3 Защита от устаревшего плана

## 7. Фронт «Звонки» — матрица встраиваний

Проверять после бэка: фронт читает то, что записали хуки.

| Встройка | Что проверить |
|---|---|
| Карточка КОМПАНИИ | контекст загружен, история по сущностям, счётчик связей |
| Карточка СДЕЛКИ с компанией | связанные лиды (все три источника), сателлиты, история |
| **Карточка СДЕЛКИ БЕЗ компании** | ✅ ничего не падает; работа ведётся от сделки; ХО/презентации редактируются; отчёт отправляется |
| Карточка ЛИДА | видна связанная сделка (если лид уже в работе); ✅ кнопка «Преобразовать в работу» НЕ предлагается, если связка есть |
| Задача | приоритетная сущность определена верно |
| Карточка звонка | контекст и история подтянулись |

Дополнительно:
- переключатель истории «По сущностям / По датам» — ✅ порядок событий логичный: **сначала «состоялось», потом «запланировано»** (одинаковое время + 1 сек);
- роли (сотрудник / руководитель группы / руководитель отдела / супер) — ✅ видимость действий соответствует.

## 9. Что смотреть при разборе проблем

| Симптом | Где смотреть |
|---|---|
| Операция висит в `queued` | лог `SalesHookOpsProcessor initialized`; Redis жив |
| Хук робота «пропал» | лог подписчика: «отброшена как повтор» — защита от дублей (300 с) |
| Поле не заполнилось | `warnings` операции: «поле не установлено» → доустановить; либо привязки SETTINGS (п. 0.3) |
| Стадия не сменилась | `warnings`: «стадия не сопоставлена» → экран стадий |
| Сделки не участвуют | `warnings`: «воронка не сконфигурирована» → админка воронок |
| Дубли не находят по ИНН | `GET /api/duplicates/domain/{domain}/field-map` — есть ли ИНН-поле; при промахе `rescan` |

## 10. Известные ограничения (НЕ баги)

- Статус CONVERTED-лида хуки не двигают — только поля и история (правило Битрикса).
- KPI/списки не изменяются ни одним из хуков (прошлое не переписываем).
- merge для сделок разных воронок не выполняется — только перепривязка.
- Более 30 открытых задач у лида: обрабатываются первые 30 + `warning`.
- Вебхуки пока без авторизации (`SALES_HOOK_WEBHOOK_AUTH_ENABLED=false`) — включать после перенастройки роботов.
