# AI-отчётность по звонкам: полное описание flow

Что происходит, зачем и где лежит каждый кусок. Документ — сводка бизнес-задачи
(apps/bot/task.report-bot.md) и реализованной системы (2026-07-21).

---

## 1. Зачем это всё (бизнес-контекст)

У отдела продаж уже есть **количественная** отчётность:

- **apps/kpi-report-sales** — сколько звонков/презентаций/КП сделал каждый
  менеджер (по списку `sales_kpi`) и телефонная статистика по длительностям
  (`voximplant.statistic.get`);
- **apps/event-sales/event-report** (`POST /event-sales/flow`) — сюда менеджер
  сам отправляет отчёт и план по событию, а бэкенд раскладывает это batch-ом
  в Bitrix: сделки по воронкам, задачи, записи в списки `sales_kpi` /
  `sales_history`.

Проблема: **кожаный мешок менеджер может пропускать, не планировать и не
отчитываться по целым кускам работы**. Количественный отчёт показывает лишь то,
что менеджер сам о себе рассказал.

Решение — параллельная **качественная** отчётность: система сама находит
звонки, транскрибирует их и анализирует AI. В итоге два независимых среза:

| | Количественный | Качественный (новый) |
|---|---|---|
| Источник | менеджер отчитался | сама запись звонка |
| Что показывает | сколько | что реально происходило |
| Где смотреть | KPI-отчёты | смарт-процесс «AI-анализ звонков», таймлайн, БД |

Реальность сегодня: срезы **сопоставляются** (агент связывает звонок с записями
отчётов). Идеал завтра: на основе качественного анализа **автоматически
заполнять** количественный (`/event-sales/flow`), переходно — по утверждению
менеджера. Для этого уже сейчас копятся flow-черновики (см. §5).

## 2. Общая схема

```
Bitrix телефония ──► cron 30 мин ──► сканер voximplant ──► дедуп ──► очередь CALL_REPORT
                                                                          │
                                          стадия TRANSCRIBE (Yandex ⇄ Vibecode) ◄─┘
                                                          │
                                          стадия ANALYZE:  ▼
   1. классификация типа звонка (tier-1, VibeCode + инструкция из базы знаний)
   2. первичный RAG-анализ: resume + recomendation ──────► ais, таймлайн сделки/лида
   3. базовый элемент смарта «AI-анализ звонков» (связи, транскрипт, резюме)
   4. ГЛУБОКИЙ РАЗБОР: 7 разделов, спич, оценки ─────────► тот же элемент (upsert
      (методички базы знаний call-analysis-{тип})           по xmlId) + ais + таймлайн
```

**Внешнего контура больше нет.** Историческая справка: до 31.07.2026 глубокий разбор
делал внешний агент (OpenClaw / claude-code) — ходил в `/api/agent/*` по ключу и
присылал результат push-back'ом. Схема не взлетела: агент нужно было поднимать и
держать отдельно, а без него конвейер доходил только до первичного резюме, и 58 из
75 полей смарта оставались пустыми. Теперь разбор считается здесь же
(`CallDeepAnalysisService`), а ручки `/api/agent/*` остались только как внешний API
для интеграций — обязательными они больше не являются.

## 3. Контур 1 — автоконвейер (apps/event-sales/src/call-report)

Шаг за шагом, с «зачем»:

1. **Cron каждые 30 минут** (`CallReportScheduler`). Kill-switch
   `CALL_REPORT_CRON_ENABLED=1`, домены — allowlist `CALL_REPORT_DOMAINS`
   (мультипортальность: каждый домен → свой `PBXService.init`, ошибка одного
   не роняет цикл). Redis-лок против наложения тиков. Перед сканом —
   **реанимация**: строки `processing` старше `CALL_REPORT_STALE_MINUTES`
   переводятся в `error`, иначе упавший воркер навсегда спрятал бы звонок.

2. **Сканер** (`CallReportScanUseCase` + `VoximplantCallsService`):
   `voximplant.statistic.get` с фильтром `'>CALL_DURATION' >=
   CALL_REPORT_MIN_DURATION_SEC` (default 300с) за окно
   `CALL_REPORT_WINDOW_HOURS` (25ч). Зачем порог: приоритет бизнеса —
   **длинные звонки/презентации**, и это же защита бюджета транскрибации.
   Анализируются **только реальные менеджеры отдела продаж**: фильтр по
   `PORTAL_USER_ID` через bx-department (`getFullDepartment(domain, sales)`,
   активные сотрудники ОП, кэш Redis сутки; выключается
   `CALL_REPORT_SALES_ONLY=0`, при недоступности department — fail-open с
   warn). В MVP берутся только звонки, чья активность принадлежит
   **сделке** (lead/contact пропускаются со счётчиком).

3. **Дедупликация**: ключ `dedup_key = "{domain}:{activityId}"` — unique-колонка
   в `transcriptions` (миграция 2026-07-21). Ключ пишет ТОЛЬКО автоконвейер;
   ручные транскрибации живут с NULL и не конфликтуют (повторная ручная
   транскрибация — легитимный сценарий). Уже обработанные (processing/done)
   звонки в очередь не попадают; `error` — попадают снова (ретрай).

4. **Очередь** Bull `CALL_REPORT` (jobId = dedup_key, attempts 2, timeout
   `CALL_REPORT_JOB_TIMEOUT_MS`), cap `CALL_REPORT_MAX_PER_RUN` звонков за тик.
   Воркер — concurrency 1: транскрибаторы и GigaChat не параллелим.

5. **Транскрибация** (`TranscriptionRouterService`, libs/call-lib): маршрут по
   длительности — **длинные (≥ `TRANSCRIPTION_YANDEX_MIN_SEC`, 600с) → Yandex
   SpeechKit** (дорогой, но надёжен на больших записях; S3 +
   longRunningRecognize), **короткие → Vibecode Whisper** (дёшево). Так
   мощности распараллеливаются, а бюджет расходуется по делу. При ошибке
   Vibecode — одноразовый fallback на Yandex. Режим можно зафиксировать:
   `TRANSCRIPTION_PROVIDER=auto|yandex|vibecode`.

6. **Первичный анализ — GigaChat RAG** (libs/ai-rag, in-process):
   `resume` (резюме от лица менеджера Гарант) + `recomendation` (рекомендации).
   Именно GigaChat, потому что **модели Vibecode не умеют RAG**, а наш RAG
   настраивается базой знаний (документы по доменам/типам). Длинные транскрипты
   идут через map-reduce (LongDialogueService). Падение LLM не роняет конвейер —
   транскрипт уже сохранён.

7. **Персист**: строка `transcriptions` (текст, провайдер, call_id,
   call_started_at, длительность, сделка) + две записи `ais`
   (type `call-resume` / `call-recomendation`, transcription_id). Это «сырьё»
   для контура 2 и для любых будущих SELECT-отчётов.

8. **Видимость менеджеру**: короткое AI-резюме — комментарием в таймлайн
   сделки. Задач-подтверждений конвейер намеренно НЕ создаёт (иначе при 10+
   звонках за тик это спам; механика подтверждения остаётся в старом ручном
   пути `/call-analysis/*`).

9. **Базовый элемент смарта** (с 31.07.2026): после стадии ANALYZE процессор
   создаёт элемент «AI-анализ звонков» — связи (сделка/лид, компания,
   контакт, менеджер), идентификация звонка, транскрипт, gigachat-резюме и
   рекомендации, тип от классификатора. Флаг едет в payload джоба
   (`createSmartItem`), ставит его сканер: cron — по
   `CALL_REPORT_CRON_CREATE_SMART` (включено по умолчанию), ручка
   `POST /call-report/scan` — одноимённым полем. Ошибка создания элемента
   НЕ роняет джоб: транскрипт и `ais` уже сохранены, а writer работает
   upsert-ом по `xmlId`, поэтому элемент дольётся следующим прогоном или
   глубоким анализом.

   До этой правки крон доходил только до БД и таймлайна, а элементы смарта
   появлялись исключительно после ручного `POST /call-report/analyze` с
   `createSmartItem=true` — расхождение с ожиданиями владельца, найденное
   при разборе прод-логов 31.07.2026.

10. **Глубокий разбор** (`CallDeepAnalysisService`, с 31.07.2026) — то, что
    раньше присылал внешний агент. Системный промпт собирается из двух частей:
    базовые правила разбора из
    `call-report/contracts/call-deep-analysis.contract.ts` (состав разделов
    строится из тех же констант `CALL_REPORT_SECTIONS`, что и поля смарта —
    рассинхрон невозможен) плюс методички портала из базы знаний
    `kind='call-analysis-{тип звонка}'`. Формат ответа зафиксирован strict
    JSON-схемой, поэтому методичка влияет на содержание разбора, но не на его
    структуру.

    Результат — тот же `AgentCallAnalysisDto`, что раньше приходил по HTTP, и
    записывается тем же `AgentAnalysisIntakeService`: ais-запись, дополнение
    смарт-элемента по `xmlId`, таймлайн разделов, дубль в карточку сделки/лида,
    пересчёт метрик речи кодом. Дублирующего кода записи нет.

    Порядок в стадии ANALYZE важен: сначала базовый элемент (каркас со связями
    и транскриптом), затем разбор. Если разбор не удался, остаётся заполненный
    каркас; повторный прогон дольёт разбор в тот же элемент.

    Env: `CALL_REPORT_DEEP_ANALYSIS_ENABLED=0` выключает шаг.

Ручные ручки (смоук/наполнение до включения крона): `POST /call-report/scan`,
`POST /call-report/analyze`, `POST /call-report/install-smart`.

## 4. Agent API (apps/event-sales/src/agent-gate) — внешний API, не обязательный

> **Статус с 31.07.2026:** глубокий разбор делает сам конвейер (см. §3, шаг 10).
> Ручки ниже сохранены как API для внешних интеграций и для ручной перезаписи
> разбора, но запускать внешнего агента для работы системы больше НЕ нужно.
> `AgentAnalysisIntakeService` из этого модуля переиспользуется конвейером
> напрямую — запись разбора у обоих путей одна и та же.

Исторически агент (OpenClaw или claude-code на отдельном сервере) по своему
расписанию делал:

1. **`GET /agent/calls`** — звонки со статусом done, по которым ещё нет
   анализа агента (keyset-обход от новых к старым — старый backlog не
   теряется). Auth: заголовок `x-agent-api-key`, ключи в env
   `AGENT_API_KEYS=имя:ключ,...` — имя агента прошивается во все его записи.

2. **`GET /agent/calls/{transcriptionId}`** — полный пакет: транскрипт,
   GigaChat-результаты, сырые сделка/компания/контакт из Bitrix, **кандидаты
   записей отчётности** из списков `sales_history` и `sales_kpi` (±14 дней),
   **активные сделки компании по воронкам ОП** (sales_base /
   sales_presentation / sales_xo — кандидаты связей, паттерн
   event-report-init через PortalModel) и **словарь pbx-полей компании**
   (код → UF-имя + enum: агент расшифровывает статусы `op_prospects`,
   `op_work_status` и т.п.). Семантическое сопоставление «какая запись/
   сделка относится к этому звонку» — работа скилла агента (анализ идёт
   постфактум, поэтому можно искать связанные по смыслу записи).

3. **`GET /agent/knowledge/all?kind={тип}&domain={портал}`** — извлечённые
   тексты материалов базы знаний: скрипты типов звонков, методички Гарант,
   клиентские уточняющие документы портала (клиентская база перекрывает
   общую). Материалы загружаются через админку «База знаний AI»
   (front /ai-knowledge) — «дообучение» скилла без деплоя.

4. **Анализ своими скиллами**: тип звонка (cold / call / presentation /
   decision / payment), статус «результативный», разбор по **семи
   формализованным разделам** (приветствие, выявление потребностей,
   презентация под потребности, работа с возражениями с причинными
   цепочками, работа по цене, закрытие, поведение при отказах) — каждый с
   **коэффициентом актуальности** (0 — не применим к типу звонка; в
   decision/payment цена оценивается обязательно, даже если работы не
   было), оценкой, разбором и рекомендациями (как ответить / альтернативы /
   что тренировать); анализ **спича** (свойство-связка-выгода); итоговая
   оценка с объяснением; рекомендации сотруднику; привязки к сделкам
   воронок и записям отчётности (confirmed/suspected).

5. **`POST /agent/calls/{id}/analysis`** (идемпотентен — ретрай не плодит
   дубликатов): мы сохраняем анализ в `ais` (type `agent-analysis`) и создаём
   **элемент смарт-процесса «AI-анализ звонков»** — всё в одном элементе,
   без лишних сущностей: связи (родитель-сделка, компания, контакт,
   менеджер-employee), crm-поля на сделки воронок (ОП основная / ОП
   Презентации / ХО — массивом `['D_id']`), привязки к элементам списков
   ОП KPI / ОП История (id + подтверждено/подозрение), транскрипт кусками
   (4 × 40k символов), GigaChat resume/recomendation, 7×4 поля разделов,
   спич, оценка+объяснение, рекомендации сотруднику. Плюс **дубль краткого
   разбора в таймлайн сделки**. Смарт — витрина клиента: вкладка на
   карточке сделки, список/канбан/фильтры Bitrix бесплатно.

Смарт устанавливается из const-конфига
(`call-report/config/call-report-smart.config.ts`) идемпотентным
`POST /call-report/install-smart`: состав полей будет меняться — добавили поле
в конфиг → повторили вызов → дольются только отсутствующие.

## 5. Flow-черновики — мост к идеалу

В push-back агент может передать `flow: { report, plan }` — черновик события
**в кодах event-sales** (resultStatus result/noresult/expired, причины
недозвона, тип планируемого события cold/warm/presentation/hot/moneyAwait/
supply, дедлайн). Это «как агент заполнил бы отчёт менеджера».

Сейчас черновики только копятся в `ais.report_result` — в
`POST /event-sales/flow` НЕ отправляются (сознательно: качеству пока не
доверяем). Дорожная карта:

1. **Сейчас**: копим черновики → сравниваем с тем, что менеджеры заполнили
   руками (`sales_kpi`/`sales_history`) → меряем качество.
2. **Переходно**: черновик показывается менеджеру на утверждение
   (механика задач-подтверждений уже существует в call-analysis).
3. **Идеал**: подтверждённые типы звонков отправляются в `/event-sales/flow`
   автоматически — качественный анализ сам порождает количественную отчётность.

Отдельные будущие алгоритмы поверх накопленной БД (всё уже доступно через
SELECT/Agent API): склейка нескольких звонков в один разговор
(call_id + call_started_at + сделка), «запланированный звонок забыт»
(план из flow-черновиков vs факт звонков), выделение успешных паттернов
каждого менеджера и персональные советы.

## 6. Где что хранится

| Хранилище | Что | Кто пишет |
|---|---|---|
| `transcriptions` | транскрипт, dedup_key, call_id, call_started_at, статус, провайдер | конвейер (upsert), ручные пути |
| `ais` | все анализы: call-resume / call-recomendation (gigachat), agent-analysis (агент, + report_item_id, + flow-черновик в report_result), call-analysis (vibecode, старый путь) | конвейер, agent-gate, ручной путь |
| Смарт «AI-анализ звонков» | витрина: поля анализа + связи | agent-gate при push-back |
| Таймлайн сделки | короткое AI-резюме | конвейер |
| Redis | дедуп-лок крона, кэш смарта (entityTypeId + enum-id), flowDto старого пути | инфраструктура |
| storage/app/ai-rag/knowledge | база знаний RAG: {domain?}/{kind}/файлы | админка «База знаний AI» |

Таймстампы `created_at/updated_at` во всех таблицах проставляет централизованно
`laravelTimestampsExtension` (libs/core/prisma) — вручную не дублируем.

## 7. Управление и документация

- env: блок «AI-отчётность» в `apps/event-sales/.env.example` (kill-switch,
  домены, пороги, роутинг транскрибации, таймауты, ключи агентов);
- инструкция для удалённых агентов и ключей:
  `apps/event-sales/src/agent-gate/REMOTE_AGENTS_GUIDE.md`;
- промпты для обучения OpenClaw скиллам продаж: `ai/agents/openclaw/`;
- админка базы знаний: front/apps/admin → «База знаний AI» (/ai-knowledge);
  стартовые материалы — retrive_data легаси-хелпера (описания продуктов
  Гарант, ~10 МБ) → загрузить в kind general;
- Swagger event-sales: тэги Call Report и Agent API.
