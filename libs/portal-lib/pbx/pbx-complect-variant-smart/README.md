# Смарт «Варианты комплекта» (complect_variant)

## Два смарта — две разные задачи

Их легко перепутать, потому что оба хранят слепок конструктора. Разница
принципиальная.

### `service_offer` — «Сервис Предложение»

**Временное хранилище данных для БУДУЩЕЙ сделки.**

У клиента есть действующая сделка на текущий период: свой комплект, своя цена,
свои документы. Менеджер начинает обсуждать следующий период — и если писать
новые цифры прямо в сделку, затрутся актуальные данные по действующему
договору. Поэтому «предложение на будущий период» живёт в отдельном элементе
`service_offer`, привязанном к текущей сделке (`parentId2`).

Когда перезаключение состоялось, робот берёт этот смарт **плюс данные RPA** и
создаёт **новую сделку отдела сервиса**. То есть `service_offer` — это
*черновик следующей сделки*, ровно один на сделку.

### `complect_variant` — «Варианты комплекта»

**Несколько предложений внутри ОДНОЙ сделки.** Про другое:

1. временно запомнить несколько собранных комплектов, пока клиент выбирает;
2. прикрепить к сделке несколько наборов комплектов, которые могут пойти
   **одним договором** (общая сетка цен местами) либо **разными**.

Вариантов на сделке много, `service_offer` — один. Первый отвечает на вопрос
«что мы предлагаем прямо сейчас», второй — «что мы предложим в следующем
периоде».

## Хранение

Слепок конструктора у обоих лежит в `bx_document_deals`. Различает их ключ:

| Строка | `serviceSmartId` | `smartId` |
| --- | --- | --- |
| обычный слепок сделки | `NULL` | `NULL` |
| предложение на будущий период | элемент `service_offer` | `NULL` |
| вариант комплекта | `NULL` | элемент `complect_variant` |

Колонка `smartId` до этого пустовала: писателей и читателей у неё не было ни в
Nest, ни в Laravel (в отличие от `offerSmartId`, который Laravel пишет до сих
пор). Миграция не потребовалась.

API: `GET /api/konstructor/deal/variants`, `GET /api/konstructor/deal/variant`,
сохранение — `POST /api/konstructor/deal` с `variantSmartId`.

## Полный круг: где мультикомплектность обязана проехать

Это то, что ещё НЕ сделано, и то, ради чего смарт заводится. Цепочка:

```
   Отдел продаж                     Отдел сервиса
   ───────────                      ─────────────
1. сделка с N вариантами
        │
2.      ├──► RPA «Поставка» ──► 3. сервисная сделка (N вариантов)
        │    (должна видеть           │
        │     все варианты)           │
        │                       4.    ├──► предложение на будущий период
        │                             │    (копия всех вариантов,
        │                             │     с правом убрать/заменить)
        │                             │
        │                       5.    └──► RPA «Перезаключение» ──► новая
        │                                  сервисная сделка (N вариантов)
```

1. **Сделка отдела продаж с несколькими вариантами.** Есть (фазы A и B).
2. **Варианты должны доехать в RPA «Поставка».** Сейчас в RPA есть только
   `service_offer_smart` — одиночная ссылка. Нужно множественное crm-поле со
   ссылками на элементы `complect_variant`, чтобы в карточке заявки было видно
   все наборы. **Не сделано.**
3. **При успешной поставке все варианты переезжают в сервисную сделку.**
   Сейчас `init-deal` копирует один слепок. Нужно копировать N строк, сохраняя
   их привязку к новым элементам смарта. **Не сделано.**
4. **Создание «предложения на будущий период» — это тоже копирование.**
   В момент создания `service_offer` делается копия текущего состояния; при
   мультикомплектности копируются все варианты, и `service_offer` обязан нести
   ссылки на них (иначе следующая сделка снова получит один комплект).
   **Не сделано** — требует поля-ссылки на стороне `service_offer`, а он
   ставится Excel-шаблоном.
5. **Перезаключение (сервис → сервис)** — тот же шаг 2–3, но источник сервисный.
   **Не сделано.**

## Что решить до кода

- **Один договор или разные.** Наборы могут идти одним договором (общая сетка
  цен) либо разными. От этого зависит вид КП, счетов, договора и отчёта о
  поставке. Сейчас и Word-DTO, и контрактный тханк, и RPA завязаны на **одну**
  пару (договор, поставка).
- **Мердж.** Слияние вариантов — не конкатенация строк, а перерасчёт: налог
  считается от договора, количество нормализуется на набор, id строк — индексы
  внутри набора. Поле `VARIANT_SOURCE_IDS` заведено под «помнить, что вошло», но
  сама операция намеренно не реализована.
- **Объём документов.** Возможно, мультикомплектные КП/договоры/счета делать
  только в новой версии фронта и поэтапно, а не сразу везде.

## Состав смарта

Поля — зеркало konstructor-полей сделки: выводятся из канона
`PBX_SALES_KONSTRUCTOR_FIELDS`, а не копируются руками (две копии списка
неизбежно разъедутся). Плюс три собственных поля варианта:

| Поле | Зачем |
| --- | --- |
| `VARIANT_NAME` | название варианта в списке |
| `VARIANT_COMMENT` | комментарий менеджера |
| `VARIANT_SOURCE_IDS` | из каких вариантов собран мегакомплект |

Стадии = статус варианта: `Черновик → Текущий → В мердже → Отклонён`.

У типа включены товарные строки (`hasProductRows` в дескрипторе) — вариант без
состава продажи бессмыслен. Ради этого в установщике const-смартов флаг
`isLinkWithProductsEnabled` стал управляемым, а `PortalSmartService` научился
заполнять `smarts.crm` (`T{hex(entityTypeId)}_`) — иначе копирование товарных
строк уходило не туда.

## Установка

Из галереи смартов в админке (`POST /api/admin/pbx/smarts/install-const`,
`kind: 'complect_variant'`). Идемпотентна по коду `complect_variant_sales`.
