# Смарт-процесс «Презентации» (`pres_sales`)

Зеркало сделок **«ОП Презентации»** (воронка `sales_presentation`) в виде
смарт-процесса. Каркас 1-в-1 с ЗПР (`pbx-zpr-smart`): один элемент = одна
презентация, стадии той же формы, связи с родительскими сущностями, анкета
(«5К» + «Хвост»), история комментариев.

> **Сделки-презентации НЕ отключаются и НЕ ломаются.** Смарт живёт
> **параллельно**: тот же отчёт менеджера продолжает двигать pres-сделки, а
> сайд-очередь `presentation-flow` дополнительно кладёт элемент смарта.
> Переезд презентаций в смарты — будущий шаг (см. «План переезда»).

## Зачем зеркало

- элементы смарта видны **вкладкой в карточке** сделки, компании, лида и
  контакта — открывать презентацию из родителя удобнее, чем искать сделку в
  чужой воронке;
- отчёт по презентациям строится по ОДНОЙ сущности (элементы `crm.item`), а не
  по воронке сделок, где презентация перемешана с продажей;
- у каждой презентации остаётся **свой снимок анкеты**: следующая презентация
  перезатирает «5К»/«Хвост» на лиде и базовой сделке, а история по каждой
  живёт в своём элементе.

## Что устанавливается

| Что | Значение |
| --- | --- |
| Код смарта в Bitrix | `pres_sales` (ключ идемпотентности) |
| Название | «Презентации» |
| `type` / `group` | `pres` / `sales` |
| Воронка | одна, `pres_main`, 8 стадий |
| Поля | все из `PRESENTATION_SMART_FIELDS` — сейчас 55 (`UF_CRM_{typeId}_PRES_*`) |
| Вкладки в карточках | сделка, компания, лид, контакт |

**Почему `type: 'pres'`, а не `presentation`:** имя `presentation` уже занято
Excel-шаблоном смарта (`SmartNameEnum.PRESENTATION`,
`install/sales/smart/presentation`). Const-ветка `ParseSmartService` матчит
шаблоны по паре `(type, group)` и перехватила бы существующий шаблон.

### Стадии (форма воронки «ОП Презентации» + контур согласования заявки)

| Код | Название | `STATUS_ID` суффикс | Семантика |
| --- | --- | --- | --- |
| `pres_new` | Заявка на презентацию | `NEW` | — (открытая) |
| `pres_approve` | На согласовании | `APPROVE` | — (открытая) |
| `pres_plan` | Запланирована | `PLAN` | — (открытая) |
| `pres_pending` | Презентация: Перенос | `PENDING` | — (открытая) |
| `pres_success` | Презентация проведена | `SUCCESS` | `S` |
| `pres_rejected` | Заявка отклонена / на доработку | `REJECTED` | `F` |
| `pres_noresult` | Презентация не состоялась | `NORESULT` | `F` |
| `pres_fail` | Отказ после презентации | `FAIL` | `F` |

Семантика задаётся **явно**: эвристика установщика по суффиксу не знает ни
`NORESULT`, ни `REJECTED`, ни того, что `NEW`/`APPROVE`/`PLAN`/`PENDING`
промежуточные. «Перенос» — намеренно ОТКРЫТАЯ стадия: перенесённая
презентация закрывается следующим отчётом, ровно как pres-сделка.

`pres_approve` и `pres_rejected` заменяют легаси-РПА «Заявка на презентацию»
(`rpa_pres_owner|manager|edu|technic|fail`): методы `rpa.*` в Bitrix24
объявлены DEPRECATED целиком. Четыре ветки согласования сведены в ОДНУ
стадию + поле `PRES_APPROVE_STAGE` — воронка не расползается, а «чья сейчас
очередь» фильтруется.

**Переходов в эти стадии flow НЕ делает** (см. «Что пишет код, что —
человек»): согласование в april-next пока ведётся руками из карточки, как и
в легаси, где переходы делали роботы портала, а не хук.

### Поля (по блокам)

- **связи** — `PRES_BASE_DEAL`, `PRES_DEAL` (своя pres-сделка),
  `PRES_TMC_DEAL` (сделка ТМЦ-заявки), `PRES_LEAD`, `PRES_COMPANY`,
  `PRES_CONTACT`, `PRES_IS_OUR_REQUEST`;
- **план/факт** — `PRES_PLAN_DATE`, `PRES_DONE_DATE`, `PRES_IS_SPONTANEOUS`,
  `PRES_RESPONSIBLE` (провёл), `PRES_PLAN_RESPONSIBLE` (назначил),
  `PRES_RESULT` (состоялась / не состоялась / перенесена / отказ),
  `PRES_MOVE_COUNT`, `PRES_MOVE_DATE`, `PRES_FAIL_REASON` (снимок причины
  отказа именно после этой презентации);
- **заявка и согласование** — `PRES_TMC_RESPONSIBLE` (кто подал),
  `PRES_OWNER` (кто утверждает), `PRES_APPROVE_STAGE` (чья очередь),
  `PRES_APPROVE_DATE`, `PRES_APPROVE_COMMENT` (за что вернули),
  `PRES_REQUEST_COMMENT` (лента комментариев согласующих),
  `PRES_IS_NEED_EDU` / `PRES_NEED_EDU_DATE`, `PRES_IS_NEED_TECHNIC` /
  `PRES_NEED_TECHNIC_DATE` / `PRES_NEED_TECHNIC_COMMENT`;
- **«5К»** — `PRES_5K_SUMMARY` + девять детальных (`PRES_5K_CLIENT_WHAT` …
  `PRES_5K_CRITERI`);
- **«Хвост»** — `PRES_XVOST`, `PRES_DECISION_CALL_DATE`,
  `PRES_DECISION_AGREEMENT`, `PRES_MANAGER_APPROACH_DATE`, `PRES_IS_OFFER`,
  `PRES_IS_COMPLECT`, `PRES_IS_PRICE`;
- **комментарии** — `PRES_PLAN_COMMENT`, `PRES_REPORT_COMMENT`,
  `PRES_COMMENTS` (накопительная лента, множественное);
- **зеркала дат** — `PRES_LAST_CALL_DATE`, `PRES_NEXT_CALL_DATE`.

> `PRES_MHISTORY` **удалено**: поле было объявлено, но не писалось ни одной
> строкой кода — на портале висел UF, который в карточке всегда пуст.
> Возвращать его зеркалом `op_mhistory` нельзя: та лента принадлежит
> КЛИЕНТУ (агрегат по всем событиям), а у элемента уже есть своя —
> `PRES_COMMENTS`. Установщик поля не удаляет: на уже установленных
> порталах `UF_CRM_{typeId}_PRES_MHISTORY` надо снять руками.

### Что пишет код, что — человек

| Блок | Кто заполняет |
| --- | --- |
| связи, план/факт, «5К», «Хвост», комментарии плана/отчёта | сайд-очередь `presentation-flow` (автоматически, из отчёта менеджера) |
| ЛЮБОЕ поле элемента, к которому владелец привязал вопрос портальной анкеты | та же сайд-очередь: ответ менеджера едет в отчёте и ложится в элемент, который этот отчёт создаёт или закрывает (в том числе в спонтанный) |
| заявка и согласование (`PRES_APPROVE_*`, `PRES_TMC_RESPONSIBLE`, `PRES_OWNER`, `PRES_IS_NEED_*`), стадии `pres_approve` / `pres_rejected` | человек в карточке (или робот согласования, настроенный на портале) |

Ответы портальной анкеты служебные поля НЕ ЗАТИРАЮТ: ключ, который поток
уже заполнил сам (стадия, результат, лента), остаётся за потоком, а
разошедшийся ответ уходит в предупреждение лога. Адрес поля берётся из
`crm.item.fields` (UF-имя → фактический camel-ключ), а не собирается
формулой — см. `libs/portal-lib/pbx/smart-item-fields`.

Так же было и в легаси: хук лишь СОЗДАВАЛ элемент РПА, а переходы по
стадиям согласования и все комментарии утверждающих делали роботы и права,
настроенные на портале вручную. Придумывать за них переходы код не может —
в april-next нет ни ТМЦ-отчёта, ни вебхука «заявка утверждена».

## Чем отличается от сделок «ОП Презентации»

| | Сделка `sales_presentation` | Элемент смарта `pres_sales` |
| --- | --- | --- |
| Где видно | воронка сделок | вкладка в карточке сделки/компании/лида/контакта |
| Анкета | сводные поля на сделке, детальные «5К» только на лиде | ВСЕ 16 ответов в элементе, снимок на каждую презентацию |
| История комментариев | `pres_comments` на клиенте (общая лента) | `PRES_COMMENTS` внутри конкретной презентации |
| Кто вёл | одно поле ответственного | «назначил» и «провёл» раздельно |
| Переносы | видно только по стадии | счётчик `PRES_MOVE_COUNT` |
| Отчётность | по воронке сделок | по `crm.item.list` одного типа |

## Что владельцу нажать

1. Админка → **Смарты** → карточка «Презентации» → **Установить**.
   Ставится идемпотентно: тип, воронка со стадиями, все поля. Повторный
   запуск дольёт недостающее и не создаст дублей.
2. Установить **поле-связь `op_presentations`** («Презентации», тип `crm`,
   множественное) на **сделке** и **компании** — через обычную установку
   полей pbx (реестр `PBX_SALES_EVENT_FIELDS`). В него сайд-очередь
   дописывает обратные ссылки на элементы (`T{hex(entityTypeId)}_{id}`).
   Без поля всё работает, просто нет обратной ссылки из карточки.
3. Ничего не выключать в воронке «ОП Презентации» — она продолжает работать.

Пока смарт не установлен, `resolveInfo` возвращает `null`, и джобы
`presentation-flow` молча пропускаются (self-gate) — отчёт менеджера не
замечает разницы.

## План переезда (будущий шаг)

1. Смарт живёт параллельно и накапливает элементы — **сейчас**.
2. Отчёт по презентациям переключается на источник `crm.item` смарта, сделки
   остаются для сверки.
3. Создание pres-сделок отключается в `SalesPresentationDealService`
   (одна ветка), элементы становятся единственным носителем; поле
   `PRES_DEAL` остаётся историей соответствия.
4. Исторические pres-сделки переносятся разовой миграцией (стадия → стадия,
   анкета → поля элемента).

## Код

- `type/pbx-presentation-smart.type.ts` — стадии, поля, items, карта переноса
  анкеты, имена UF/camel;
- `type/pbx-presentation-smart-field.type.ts` — `buildPresentationInstallFields`
  / `buildPresentationInstallCategories` (контракт pbx-install);
- `type/pbx-presentation-smart.descriptor.ts` — карточка галереи;
- `pbx-presentation-smart.service.ts` — `resolveInfo` (PortalModel → PortalDB)
  и `mirrorFields`;
- установка — `@app/pbx-install/smart/presentation` поверх общего движка
  `InstallConstSmartService`;
- сайд-очередь — `apps/event-sales/src/presentation-flow`.
