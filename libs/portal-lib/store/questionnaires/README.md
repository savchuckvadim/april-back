# Портальный каталог анкет — модуль хранения

Состав вопросов, которые менеджер заполняет при планировании и при отчёте,
задаёт **портал**, а не код фронта. Причина (словами владельца): «заранее мы
можем не знать чек-листы и поля для заполнения».

Полный план, решения и история — `front/docs/event-questionnaire-catalog.tasks.md`.

## Что здесь лежит

| Файл | Роль |
|---|---|
| `portal-questionnaires.schema.ts` | Реестр допустимых значений и матрица «тип отображения ↔ тип поля». Источник правды для `GET /schema`. |
| `portal-questionnaires.dto.ts` | DTO чтения и сохранения + мапперы «запись → DTO». |
| `portal-questionnaires.repository.ts` | Интерфейс хранилища. |
| `portal-questionnaires.prisma.repository.ts` | Реализация: одна транзакция на сохранение, `version++`. |
| `portal-questionnaires.service.ts` | Валидация на сохранении, компиляция каталога для фрейма, Redis-кэш. |
| `portal-questionnaires.controller.ts` | Админ-CRUD `admin/portal/:portalId/questionnaires`. |
| `portal-questionnaires.module.ts` | Лёгкий модуль без контроллеров — его импортируют приложения. |
| `portal-questionnaires.admin.module.ts` | То же + админ-контроллер. |

Соседи, которые доделывают картину: `back/apps/admin/src/portal/questionnaires`
(живые поля Битрикса, заведение поля, сверка привязок),
`back/apps/event-sales/src/questionnaires` (чтение фреймом),
`back/libs/portal-lib/pbx/event-type-registry` (связь «тип события → смарт»).

## Правила, которые здесь держатся

**Валидация на СОХРАНЕНИИ, а не при рендере.** Портал не должен уметь
сохранить то, что фрейм не исполнит: неизвестный контрол, канал или вид
условия, множественное поле, «требовать новое значение» вне канала CRM, срок
годности у не-даты, вариант списка без `bitrixId`, анкету вовсе без условий.
Иначе менеджер увидит пустое место, и никто не поймёт почему.

**Реестр не шире движка.** Значение появляется здесь, только когда фрейм
исполняет его сегодня либо учится тем же заходом. Реестр, который «шире»
движка, — это обещание, которое приложение не выполнит молча.

**Мягкая привязка к полю, без FK на `bitrixfields`.** Переустановка смарта
или компании сносит все строки полей сущности (`deleteFieldsByEntityId`) —
анкета молча опустела бы. Якорь — `field_name`, полное UF-имя ровно как его
вернул Битрикс; собирать имя конкатенацией нельзя.

**Ответов здесь нет.** Источник правды по ответам — поля CRM и элементы
смартов. Своя таблица ответов стала бы четвёртым источником правды рядом с
CallChecklist, AfterPresentation и XvostFields.

**Код вопроса ≠ код поля.** Код вопроса — ключ ответа во фрейме
(`кодАнкеты:кодВопроса`). Два разных вопроса могут писать в одно поле и не
делить между собой значение, статус сохранения и таймер автосохранения.

**Гасим, не удаляем.** Пункт и вариант справочника выключаются
(`is_active = false`): уже собранные в CRM ответы иначе становятся
необъяснимыми.

## Кэш

`resolve(domain, appCode)` кэширует скомпилированный каталог в Redis на 5
минут, ключ версионирован. `save()` сбрасывает кэш домена. Redis недоступен —
предупреждение и работа без кэша, а не 500.

Фрейм сверяется по паре `version` + `hash` (sha1 нормализованного состава):
состав не менялся — состав не перечитывается.

## Что уезжает во фрейм

Пункты со сломанной привязкой (`field_status !== 'ok'`) на канале CRM в
компиляцию **не попадают**: фрейму незачем знать про сломанные привязки, и
они не смогут заблокировать отправку отчёта. Поле и варианты уезжают
готовыми — UF-имя и `bitrixId` элементов, чтобы фрейму не нужен был слепок
портала. Исключение — канал смарта: `bitrixId` его элементов фрейм не
получает и не должен, перевод в формат Битрикса делает бэк.

## Тесты

`portal-questionnaires.service.spec.ts` — валидация и компиляция;
`portal-questionnaires.prisma.repository.spec.ts` — транзакция и гашение;
