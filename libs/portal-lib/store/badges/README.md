# Портальный каталог бейджиков — модуль хранения

Бейджик — готовая формулировка, которую менеджер ставит одним нажатием в
комментарий отчёта («Просил перезвонить позже») или в название планируемого
события («Звонок», «Выслать КП»). Решение владельца 27.10.2026: требование
«напиши комментарий» не создаёт смысл, а создаёт «0», «ндз», «asdf» —
поэтому не усиливаем валидацию, а убираем причину печатать мусор.

Постановка и решения — `ai/tasks/2026-10-27-comment-badges-plan.md`.

## Что здесь лежит

| Файл | Роль |
|---|---|
| `portal-badges.schema.ts` | Реестр: цели, режимы, итоги работы, типы событий, цвета; типы документа. Источник правды для `GET /schema`. |
| `portal-badges.defaults.ts` | Общий набор из кода — действует в режиме «по умолчанию», заготовка для «своих». |
| `portal-badges.document.ts` | Терпимый разбор документа из JSON (мусор отсеивается построчно). |
| `portal-badges.repository.ts` | Контракт хранилища + реализация поверх `portal_app_settings`. |
| `portal-badges.service.ts` | Валидация на сохранении, компиляция действующего набора, Redis-кэш, hash. |
| `portal-badges.dto.ts` | DTO реестра, сохранения, админского и фреймового ответов. |
| `portal-badges.controller.ts` | Админ-редактор `admin/portal/:portalId/badges`. |
| `portal-badges.module.ts` | Лёгкий модуль без контроллеров — его импортируют приложения. |
| `portal-badges.admin.module.ts` | То же + админ-контроллер. |

Чтение фреймом — `back/apps/event-sales/src/badges` (`GET /badges?domain=`).

## Правила, которые здесь держатся

**Хранение без миграций.** Документ лежит одним ключом `comment_badges` в
JSON-колонке `portal_app_settings.settings` приложения `event-sales`.
Миграции живут в Laravel-проекте `online`; JSON при upsert сливается, и
чужие ключи сохранение не трогает. Реестр скалярных настроек этот ключ не
знает и пропускает — конфликтов с «Настройками приложений» нет.

**Режим «по умолчанию» не требует записи в БД.** Портал без документа
получает общий набор. Свой набор действует только в режиме `own`; в режиме
`default` он сохраняется, но не применяется — переключение туда-обратно
ничего не теряет.

**Валидация на СОХРАНЕНИИ.** Коды уникальны; цели, итоги, типы и цвета —
из реестра; у комментария нет типов события, у названия нет итогов;
основной бейджик названия (`isDefault`) — один на тип. Иначе фрейм получил
бы запись, которую не исполнит, и молча её не показал.

**Реестр не шире движка.** Коды итогов работы — `WorkStatusCode` фрейма
плюс факт `presentationDone`; типы событий — коды справочника планов
`EV_PLAN_CODE`. Новое значение появляется здесь только вместе с поддержкой
во фрейме.

**Название события: слово типа не пишем.** Заголовок задачи бэк собирает
сам как «<тип>  <название>  <контакт>», поэтому согласованное «Звонок + имя
клиента» фрейм получает, подставляя в поле одно имя клиента. В общем наборе
основного текста типа нет; портал может завести свой (`isDefault`) — тогда
подставится «<текст> — <клиент>».

**В группе «не дошёл до нужного человека» профессии не называем** —
должность менеджер дописывает сам. Группы «не дозвонился» нет: на gsirk её
закрывает функция «недозвон».

## Кэш

`resolve(domain)` кэширует действующий набор в Redis на 5 минут; `save()`
сбрасывает кэш домена. Фрейм сверяется по `hash` (sha1 состава): совпал —
состав не перечитывается. Redis недоступен — предупреждение и работа без
кэша.
