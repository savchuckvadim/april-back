централизованная работа с битрикс отделом(продаж или сервиса)

Используется практически во всех приложениях

Для фронтенда наружу ендпоин идет через приложение
PBX
Также используется бэкенд приложениями
Используется часто, поэтому полученные из битрикс данные кэшируются в redis
(TTL сутки, ключи содержат домен и день: `department_*`, `department_structure_v3_*`, `bx_team_*`)

Руководители отдела — список `HEADS` (руководитель первым, потом заместители):
объединение ролей участников узла новой структуры (REST 3.0 `humanresources.node.get`,
`BxDepartmentHeadsService`, узел ищется по `accessCode = 'D' + ID`) и легаси `UF_HEAD`.
`UF_HEAD` в ответе = `HEADS[0] ?? null`. Без скоупа `humanresources` на вебхуке
остаётся только `UF_HEAD` (warn в лог, ответ не падает).

Суперпользователь вендора (сотрудник April) — `BxSuperUserService`, env
`BX_SUPER_USER_IDS` в формате `domain:id[,domain:id...]` (домен без учёта регистра,
мусорные записи — один warn). В `bx/department/structure` он получает
`currentUser.isSuperUser = true`, `visibility = all`, `headOf = cup`,
`headOfDepartmentIds` — все ОП, `headOfSource = superuser`; `isHead` и коллеги — по
структуре. У остальных `isSuperUser = false`, userId ≤ 0 — никогда. Фронты больше не
угадывают его по фамилии. ai-analytics (kpi-report-sales) даёт ему роль cup без чтения
структуры, но слепую калибровку РОПов (rop-mark) — только на чтение.

Сброс кэша:
- каждый эндпоинт принимает необязательный `resetCache: boolean` — кэш игнорируется
  и перезаписывается свежими данными из Битрикс
- `POST bx/department/cache/reset` c телом `{ domain }` — сброс по одному порталу,
  с пустым телом — по всем порталам сразу (BxDepartmentCacheService, SCAN по паттернам)
- redis общий для всех приложений монорепы, поэтому сброс действует на все приложения

Идея
1 ** 
Сделать обновление всех department по crone
Тогда при запросе из apps будет всегда получать из кэша - так быстрее.
Данные department в redis будут обновляться раз в час.
А логика будет всегда брать из редис без проверок на протухшесть

Даже если crone почему-то не отработает - в app будет просто доступен старый (предыдущий department)
